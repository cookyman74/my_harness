## 2. dogfood 에서 잡은 거짓 통과 3종 — 이 작업의 실질

스텁 테스트 20건이 전부 GREEN 이었는데, **실제 `claude` CLI 로 한 번 돌리자 4/4 통과가 전부 허위**였다.
"검사가 도는 것처럼 보이는데 실제로는 0건을 검사하고 통과한다"는 이 레포의 지배적 실패 계열이
**내가 방금 만든 채점기에서 그대로 재현**됐다.

| # | 거짓 통과 | 원인 | 수정 |
|---|---|---|---|
| 1 | 1회 실행이 **2회**로 집계 | `input` 을 flat 직렬화하면서 `description` 이 `command` 와 같은 문자열을 담았다 | `DESCRIPTIVE_KEYS` 제외 |
| 2 | 대조할 주장이 없는데 `passed:true` | `report_matches_calls` 가 "주장 0건"을 통과로 셌다 | `vacuous:true` 표시 + summary 집계 + 표준출력 경고 |
| 3 | **실행 1회 + 참조 1회**를 "2회 실행"으로 집계 | 텍스트 출현 수는 `Bash` 실행과 `Read` 참조를 구분 못 한다 | `tool` 한정(`"tool":"Bash"`) |

수정 후 같은 실행을 재채점하니 **3/4 통과 · 1건 공허**로 바뀌었다.
`retried` 는 실제로 **감사를 1회만 실행**했으므로 `false` 가 정답이다.

> **교훈:** 스텁만으로 통과한 검사는 신뢰할 수 없다. 세 결함 모두 **실제 CLI 출력의 실제 필드 구조**를
> 봐야만 드러났다. 계약 테스트는 필요조건이지 충분조건이 아니다.

## 6-1. 외부 리뷰 인프라 자체의 결함 (이 작업의 부수 산출)

리뷰를 돌리다 **정본 `run-review.sh` 의 결함**을 찾았다. 산출물 러너가 아니라 **검증 장치**가 조용히
오작동하고 있었다.

- **`REVIEWERS_OVERRIDE` 가 아예 없었다.** 호출자가 넘겨도 무시되니, 엔진별로 스크립트를 두 번 띄우면
  **네 프로세스가 같은 산출물 파일에 동시에 썼다.** 실측 피해: 한 리뷰 파일 안에 "새 결함 없음"과
  "[HIGH] 2건"이 문장 중간에서 뒤섞여 공존 → **어느 판정도 신뢰할 수 없어 R11 을 무효 처리**했다.
- **`run_with_timeout` 의 600s 가 하드코딩**이라 늘릴 방법이 없었다 — codex 가 **3라운드 연속** `rc=124`
  로 판정 없이 죽었다. 정본이 시간을 박아두면 프롬프트가 큰 리뷰는 영영 완주하지 못한다.

수정: `REVIEWERS_OVERRIDE` 실동작 + **stage 락**(`mkdir` 원자성으로 동시 실행 거부) + 자기검증
`degraded` 자동 기록 + `REVIEW_TIMEOUT` env + 문서에 "한 단계에 한 번만 띄운다" 규약.

> **이전 라운드 장부의 신뢰도:** 지적 자체는 대부분 실패하는 테스트로 재현해 유효하다. 그러나
> **어느 엔진이 무엇을 냈고 언제 실패했는지**는 이 결함의 영향을 받았다. 그대로 기록한다.

| 패턴 규약 오류 | R4 에 "패턴을 실행 형태에 고정하라"고 적었는데, 실측에서 에이전트가 `scripts/x.sh` 를 접두사 없이 실행해 **거짓 실패**가 났다. 화이트리스트 덕에 `"command": <값>` 형태가 되므로 **실행 필드 이름에 고정**이 옳은 관용구다 |

### 기각한 지적 3건 (방향은 맞고 처방이 틀렸거나, 재현 안 됨)

| 지적 | 기각 사유 |
|---|---|
| `--ignore-user-config` 추가(agy R1) | **그런 플래그가 존재하지 않는다**(`claude --help` 확인). 넣었으면 러너가 전부 깨졌다 |
| `env` 에 `os.environ` 전체(agy R1) | **산출물에 시크릿을 쏟는다.** 큐레이트한 항목만 기록 |
| `cut()` 재귀 깊이 가드(agy R3) | **재현 안 됨.** depth 2000+ 는 `json.dumps` 자체가 실패해 CLI 가 그런 줄을 못 만들고, 손으로 만든 depth 3000 은 `json.loads` 가 먼저 RecursionError 를 내 러너가 그 줄만 버린다(실측) |
| "RC 비0인데 STATUS ok"(codex R5) | **사실이 아니다.** `[ "$RC" = 0 ] \|\| STATUS=unmeasurable` 이 실재하고 테스트 G 가 증명한다 |
| `RC!=0` 이 partial 을 unmeasurable 로 덮어써 정보를 숨긴다(codex R9) | `runner_rc`·`dropped_lines` 가 manifest 에 남아 **정보 손실이 없고**, 비정상 종료한 실행을 "측정됐다"고 부르는 쪽이 더 위험하다. 요약 라벨만 보수적인 쪽이다 |

`MANAGED_RELS` 제외 제안(agy R2/R3)은 **부분 기각**했다 — 빼면 2026-08-07 결함(화이트리스트 누락 →
영영 미갱신)이 되살아난다. `NEW_EXCLUDE_RELS` 를 신설해 **신규 자동배포만 막고 갱신은 유지**했다.

> **확인 과정에서 진짜 결함을 찾은 사례:** agy R3 의 재귀 지적을 재현하려다, 파싱 실패 줄이
> **아무 기록 없이 사라지는** 것을 발견했다. 지적 자체는 기각했지만 그 옆의 실재 결함을 얻었다.

## 8. ⚠ 실측: `--allowedTools` 가 강제되지 않는다 (2026-09-03)

9케이스를 돌리자 채점기의 `화이트리스트 없는 도구` 경고가 떴다. 확인해 보니 **목록에 없는 도구가
전부 사용되고 있었다** — `Write` 6 · `Edit` 1 · `ToolSearch` 5 · `Skill` 2 · MCP 11회.

단독 재현: `--tools "Read"` 만 주고(옵트인 없음) "파일을 만들라"고 하자 모델이 `Write`·`Bash` 를 써서
**실제로 파일을 생성했다.**

> **즉 `BENCH_ALLOW_EXEC` 옵트인 게이트는 실효가 없다.** 문자열은 검증하지만 CLI 가 강제하지 않는다
> (`--permission-mode bypassPermissions` 가 필터를 무력화하는 것으로 보인다 — 원인 미확정).
> **내가 만든 안전장치가 바로 이 레포의 지배적 실패 계열("검사가 도는 것처럼 보이는데 안 돎")이었다.**

**대응:** 러너 헤더와 `self-improvement-loop.md` 에 실측을 그대로 적었다 — 옵트인은 **의도 기록일 뿐
강제가 아니며**, "기본이 Read 뿐이라 안전"은 틀린 읽기다. 격리된 작업 사본에서만 돌리고, 진짜 봉쇄가
필요하면 컨테이너 등 프로세스 밖 수단을 써야 한다.

### 8-1. 해결 — `--disallowedTools` 로 전환 (2026-09-03 · 외부리뷰 없이 실측만)

세 조합을 같은 프롬프트("PWNED.txt 를 만들라")로 비교했다:

| 조합 | 세션 노출 도구 | `Write`/`Bash`/`Edit` | MCP | 파일 생성 |
|---|---|---|---|---|
| `--allowedTools Read` (이전 러너) | 70 | **전부 남음** | 37 | **됨** |
| `--disallowedTools Write,Edit,Bash,…` | 30 | 제거 | 37→**우회됨**(`ctx_execute` 로 `date` 실행) | 차단 |
| 위 + `mcp__*` | 30 | 제거 | **0** | 차단 |

**`--allowedTools` 는 도구를 하나도 빼지 않는다.** "권한 프롬프트 없이 허용"의 뜻이라 `bypassPermissions`
하에선 무의미하다. `remediate.ts`(M15)가 `--disallowedTools "*"` 를 쓴 이유가 실측으로 설명된다.
**MCP 도구가 우회 경로였다** — 셸 실행을 제공하는 MCP 가 있으면 코어 도구를 다 막아도 뚫린다.

러너를 **허용 목록의 여집합을 `--disallowedTools` 로 넘기고 `mcp__*` 를 항상 막는** 방식으로 바꿨다.
러너 경유 실제 실행: `Write` 호출 → `No such tool available: Write. Write is disabled` 거부, 파일 미생성.
`BENCH_LIVE=1` 테스트(BU)가 **실제 CLI 로** 이를 검증한다(스텁으로는 증명이 안 된다 — 이 세션의 교훈).

> **여집합 방식의 영구 한계:** 목록 밖 도구는 못 막는다. 1차에 `TaskCreate`, 2차에 `DesignSync`·
> `ListMcpResourcesTool` 이 통과했다 — **목록은 영원히 뒤처진다.** 부작용 없는 도구들이었지만 그건 운이다.
> 그리고 도구 봉쇄일 뿐 샌드박스가 아니다. `Bash` 를 허용하면 작업디렉토리 밖이 열린다.

> **확인 과정의 자기 오판:** 첫 C·D 시도에서 "도구 0회·파일 0개"가 나와 성공으로 읽을 뻔했다.
> 실제로는 인자 배치 오류로 **CLI 가 아예 실행되지 않은** 것이었다(`Input must be provided`).
> 0 은 "막혔다"와 "안 돌았다"를 구분하지 못한다 — `init` 이벤트의 도구 수로 다시 확인했다.
