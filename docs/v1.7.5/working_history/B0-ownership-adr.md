## 1. 무엇을 정했나

BEHAVIOR 도입(B1~B5) 전에 **"같은 요구가 정의·절차·BEHAVIOR 에 흩어지는" 재발**을 막는 것이 목표였다.
7개 결정으로 답했다.

| | 결정 | 요지 |
|---|---|---|
| D1 | 단일 정본 | BEHAVIOR 가 소유. **단 BEHAVIOR 가 없는 요구는 정의가 정본**(B1 은 권장이지 필수 아님). 정의는 **참조**한다 |
| D2 | 파생물 | **파생하지 않는다.** 생성기·재생성 시점·승인 경로가 전부 미실재라 파생을 넣으면 새 drift 축이 생긴다 |
| D3 | drift 검출 | **별도 검사**(`check-behaviors.sh`) · 4축에 얹지 않는다 · **구조적 참조 무결성까지**(의미 일치는 검출 안 함·공백 명시) |
| D4 | lifecycle | 삭제=dead 참조 fail · rename=삭제+신설(자동 추적 없음) · **holdout 은 해당 없음**(실측 0건) |
| D5 | 실행 테스트 동기화 | `Intent`·`Failure modes` 변경 → 참조 정의의 트리거 쿼리 재검토 + **결과서 4필드 기록**. 자동 강제 없음 |
| D6 | UI 노출 | 4축 카드 1개 유지 · BEHAVIOR 는 진단 접기 안 · **`Axis` 유니온 4개 고정** · B1=CLI 까지, UI 는 **B5** |
| D7 | 채점 중립성 | 축별·검사별 입력 계약을 표로 확정. **규약을 지킬수록 감점되는 구조**를 제거 |

**② 행동 요구 판별 = 내용 유형·문장 단위**. 둘 다 유효하고, 폐기된 것은 R3 의 "섹션명 단위" 하나뿐이다.

## 3. 배운 것

### (1) "수정이 수정을 부른다"가 이 단계의 지배적 실패 모드였다

R20~R31 의 agy HIGH 12건 중 **8건이 내가 직전 라운드에 넣은 수정 자체의 결함**이었다.

- R26 — 닫히지 않은 코드펜스를 "포인터 0개 → 필수 섹션 미충족 → 과락"이라는 **연쇄**로 막으려 했는데,
  **펜스 안 내용이 실체로 세어져** 오히려 통과했다. 막으려던 것을 정확히 반대로 만들었다.
- R28 — 그래서 FOR-EACH 검사를 조건으로 신설했더니, R31 에서 **`completenessMissing` 과 중복 소유**가
  드러났다(같은 사실에 두 번 감점).
- R30 — R29 에서 층 구분을 **덧붙이기만 하고** 모순되는 옛 서술("R4 가 R2 를 대체")을 안 지웠다.

패턴은 하나다: **간접 논리에 기대면 전제가 바뀌는 순간 반대로 작동한다.** 직접 판정으로 바꾸고,
설명을 덧붙였으면 **덧붙인 만큼 옛 서술을 지웠는지** 확인해야 한다.

### (2) 문서를 고칠 땐 "이 문장이 다른 어디에 복사돼 있나"를 먼저 본다

R29(계획서엔 있고 ADR 엔 없던 R25 규칙)·R30(계획서가 옛 대체 논리를 복사)·R28-③(제안서 §5 가 stale)
셋 다 **같은 사실이 3개 문서에 흩어져 있어** 한 곳만 고친 데서 났다. 정본 1 + 사본 2 구조를 인지하고
매 수정마다 3곳을 함께 본다. 제안서 §5 에는 **"실행 정본은 계획서"** 라고 못 박아 두었다.

### (3) 엔진이 갈리면 정보는 소수 쪽에 있었다

R20~R31 은 codex 가 12연속 "HIGH 없음"인 동안 agy 만 지적했고, **12건 전부 검증 결과 실재**했다.
"한쪽이 clean 하니 됐다"고 읽었으면 12건을 다 통과시켰을 것이다. **엔진 불일치는 수렴 신호가 아니라
탐색 신호**다. 반대로 R32·R33 은 둘 다 clean 이었고, 그때 비로소 닫았다.

## 5. 범위 밖에서 관측한 팩토리 정본 결함

**`build-scorecard.sh` 가 빈 원장을 무경고 통과시킨다.** `issues` 키가 없거나 비면
`confirmed=0 · alignment_score=null · warnings=[]` 를 쓰고 `emit-loop-scorecard.sh` 는 **"발행"**
으로 보고한다(실측: `eval_status` 는 `ok` 이므로 기만 검사에도 안 걸린다). 이 세션에서 실제로
한 번 당했다 — emit 에 verdicts 대신 scorecard 를 넘겼는데 성공으로 보고됐다.

이것은 팩토리가 이미 두 번 고친 계열(한글 enum 무경고 집계 0 · emit 성공 오보)의 **세 번째 변종**이다.
`issues` 가 비었으면 `eval_status: "eval-empty"` 로 낮추고 경고해야 한다.
**정본 변경은 중대 blast-radius(stabilizer 게이트)이므로 여기서 고치지 않고 기록만 한다.**
