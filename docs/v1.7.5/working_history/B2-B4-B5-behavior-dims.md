## 1. 무엇을 만들었나

**B2 — 채점 중립성.** 판단 기준을 BEHAVIOR 로 옮겨도 점수가 떨어지지 않게 했다.
검사별로 입력을 나눈 것이 핵심이다 — *내용을 옮겨 빠져나갈 수 있는 검사는 합성 body,
정의 파일 자체의 형태를 보는 검사는 원본*. 선결 2건(필수 섹션 3종→5종 통일 · D7 구현)을
먼저 처리했고, 파서 4종(`parseBehaviorRefs`·`scanPointers`·`splitSections`·`readBehaviorBodies`)을
새로 만들었다.

**B4 — 삭제 가드.** E3(계층B 삭제 판정)이 붙기 **전에** 세우는 방어선이다. 4층 AND:
①결정적(필수 섹션·제약 어휘) ②정적 대응(토큰 겹침) ③**의미 판정기** ④동적 게이트.
E3 전에는 ③④가 없으므로 **어느 문장도 자동 삭제되지 않는다** — 의도된 상태다.

**B5 — 진단 연결.** ADR D6 의 "진단 접기 안에 보인다"를 실제로 구현했다. 새 `FindingType` 을
만들지 않고 기존 `dead_link`·`orphan` 에 `subject_kind: "behavior"` 로 얹었다.

## 2. 지배적 실패 계열 — "같은 규칙의 두 구현이 갈라진다"

세 단계에서 나온 HIGH 36건 중 **17건**이 이 계열이다. 서버가 셸을 부를 수 없다는 아키텍처
결정(ADR D5) 때문에 같은 규칙을 TS 와 bash 에 각각 구현했는데, **구현이 둘이라는 게 판정이
둘이어도 된다는 뜻은 아니었다.**

갈라진 축들:

| 축 | 어느 쪽이 틀렸나 |
|---|---|
| 스펙 유효성 | TS 가 파일 존재만 봄 |
| 정의 형식 오류 | TS 가 조용히 건너뜀 |
| BOM·frontmatter 미종료 | TS 만 관용 |
| 심링크·크기 정책 | CLI 만 관대 |
| 코드펜스 안 heading | CLI 만 못 봄 |
| CommonMark fence 길이 | **양쪽 다** `slice(0,3)` 축약 |
| HTML 주석 | **양쪽 다** 미추적 |
| 블록 스칼라 안 key-like 줄 | CLI 만 오탐 |
| 순회 상한 | TS 에만 존재 |
| 차원 heading 매칭 | TS 가 `includes`, CLI 가 exact |
| 들여쓴 비항목 | TS 가 앞 참조까지 버림 |
| 수평선·heading 실체 판정 | **양쪽 다** ADR 정의 미구현 |

**대응은 `behavior-parity.test.ts` 였다.** 두 구현의 판정을 **직접 대조**하는 테스트를 37건까지
키웠고, 새 규칙을 넣을 때마다 그 입력을 패리티에 추가했다. 이것이 지금 유일하게 작동하는 방어다.

## 3. 배운 것

### (1) 한쪽만 고치면 반대 방향으로 갈라진다 — 5회

`B2 R3` 에서 TS 의 블록 스칼라 오탐을 고치며 "CLI 는 이 오탐이 없다"고 **실측 확인했다.**
그런데 그건 **그때 테스트한 입력에 한해서**였고, `B5 R4` 에서 `notes: |` 아래 `behaviors:` 같은
입력으로 반대 방향 갈라짐이 드러났다. 같은 일이 주석 추적(B2 R4)·무효 스펙 합성(B2 R8)·
순회 상한(B5 R8)·들여쓴 비항목(B5 R6)에서 반복됐다.

**"확인했다"는 확인한 입력에 대해서만 참이다.** 규칙을 바꿀 때 패리티 케이스를 함께 넣지
않으면 다음 라운드에 반대편이 나온다.

### (2) 내 수정이 새 결함을 만든 경우 — 6회

- `B5 R5` → `B5 R6`: "TS 가 조용히 통과한다"를 고치려다 **보고 대신 버리기**로 구현해,
  앞의 유효 참조까지 없앴다. 고칠 것은 "보고하지 않음"이지 "참조를 읽음"이 아니었다.
- `B4 R1` → `B4 R3`: `dynamicGate` 를 AND 로 넣으면서 "대응 미발견도 막는다"는 **머리말은 안
  고쳤다** — 주석과 코드가 반대로 말한 채 두 라운드를 보냈다.
- `B2 R4` → `B2 R7`: 주석 추적을 두 함수에 각각 넣고 **그 사이 경계를 안 봤다**.
  섹션 경계에서 상태가 끊겨 그 자체가 우회 통로가 됐다.

### (3) 열거는 끝나지 않는다 — 그러나 대안이 없을 때도 있다

`description` 빈 값 판정은 5번, 제약 어휘는 3번 뚫렸다. 앞의 것은 **허용 규칙**으로 뒤집어
끝냈다(받을 형태만 열거). 뒤의 것은 이 단계가 의미 판정을 안 쓰기로 했으므로 열거를 피할 수
없었고, 대신 **어간 + 활용 음절**로 축을 바꿔 어미 축을 닫았다.

판단 기준은 **비대칭**이었다: 놓치면 보존 대상이 삭제되고, 과탐하면 제안에 머문다.
그래서 과탐을 택했고, **과탐 경계도 테스트로 고정**했다 — 1층이 다 잡으면 2층이 영영 안 돈다.

### (4) 문서가 정한 것을 구현이 안 지킨 사례

`B2 R5` 는 ADR 이 명시한 "실체 줄" 정의(수평선·heading 제외)가 **구현에 아예 없던** 경우다.
R10 codex 가 MED 로 정의를 요구해 ADR 에 적혔는데 구현 단계에서 누락됐다.
`B4 R6` 은 반대로 **설계서가 stale** 이었다 — 스킬 필수 섹션의 `why` 관례가 실재하지 않아
(6/6 전부 새 finding) 코드가 아니라 설계서를 고쳤다.

이후 **코드 ↔ SKILL.md ↔ 설계서 3자 정합 테스트**를 넣었다.

## 4. 판단해서 안 고친 것

| 항목 | 판단 |
|---|---|
| **TOML 에이전트의 `behaviors` 참조** | ADR 이 frontmatter 배열만 정의했고 TOML 문법은 **정하지 않았다.** 검사기가 발명하면 ADR 없는 계약이 생긴다 → **조용한 축소를 명시적 "미지원" 보고로** 바꾸고 ADR 개정을 선행 조건으로 기록 |
| **순회 상한 제거** | 전수 스캔은 OOM 방어를 포기하는 것이다 → 상한을 유지하되 **양쪽이 똑같이 끊고 그 사실을 보고** |
| **필수 섹션 부분 일치** | 정본 관례가 부분 일치다 → 엄격해지는 것은 **BEHAVIOR 6차원**뿐 |
