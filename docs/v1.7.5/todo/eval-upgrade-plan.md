## B2 — 에이전트 정의에 행동 차원 도입 `⬜ 미착수`

**목표:** 6차원(Intent·Evidence·Decision·Execution·Recovery·**Failure modes**)을 권장으로 추가.
**등급:** 경량 · **근거:** 제안서 §3 B2

> ⛔ **착수 전 필수 ①(ADR-001 R12):** **필수 섹션 목록이 문서와 코드에서 다르다** — `SKILL.md:113` 은 에이전트 5종(핵심 역할·작업 원칙·입출력 프로토콜·에러 핸들링·협업)인데 `artifacteval.ts:166` 은 **3종**(`역할`·`프로토콜`·`에러`)만 검사한다. ADR 이 "정의 소유라 본문 필수"라 한 **`협업` 이 채점에서 아예 빠져 있다.** 어느 쪽으로 통일할지 결정하고, **코드를 바꾸면 기존 하네스 점수 변화를 실측해 보고**할 것(모든 하네스 점수가 바뀌는 변경이다).
>
> **순서:** ①을 먼저 확정하고 그 결과를 **ADR D7 의 필수 섹션 목록**에 반영한 뒤 ②를 구현한다(소유별 표는 R15 에서 폐기됐다 — 채점은 소유를 판정하지 않는다). **①이 ②의 입력 계약을 정한다** — 건너뛰면 어느 목록을 검사할지 알 수 없다(R13 양 엔진).
>
> ⛔ **착수 전 필수 ②(ADR-001 D7):** BEHAVIOR 를 도입한 정의가 **그 이유만으로 감점되지 않도록** 채점을 먼저 고친다. `scoreInduction` 은 명령형 줄 비율이라 판단 기준을 BEHAVIOR 로 옮기면 점수가 떨어진다(`artifacteval.ts:142-148`) — 행동 차원을 권장하면서 따르면 손해인 상태로 두면 안 된다. **참조 대상 BEHAVIOR 본문을 정의 채점 입력에 합성한다**(단일안 — "induction 축만 제외"는 채점 우회 통로라 폐기). **축별·검사별 입력이 다르다**(ADR D7 두 표): `trigger`=정의 description · `induction`·`pruning`=합성 body · `scoreStructure` 는 **검사마다** 다르다 — 필수 섹션·본문 부실·**references 분리 판단**=정의 body(합성 전), **줄 수 상한·대용량 코드펜스=합성 body**(둘 다 `range` 생략·`why` 에 출처 표기). 원칙: *내용을 옮겨 빠져나갈 수 있는 검사는 합성, 정의 파일 자체의 형태를 보는 검사는 원본.* 추가 계약 2가지 — ① 줄 수 상한 finding 은 **`range` 생략**(합성 줄 수는 정의 파일에 없는 줄을 가리킨다)·`why` 에 내역 표기 ② **`behaviors:` 선언 정의의 "본문 부실" 판정은 줄 수가 아니라 구조로 — **4조건 전부**(ADR D7): ⓐ 필수 heading 전부 ⓑ 끊긴 참조 0 ⓒ **참조 BEHAVIOR 가 비어 있지 않음**(B1 검사 결과를 채점기가 소비) ⓓ **정의에 실체가 남아 있다** — 필수 섹션 중 **최소 하나**에 참조 포인터가 아닌 실제 본문(소유를 묻지 않는다). 전부 포인터뿐이면 껍데기다. `scoreStructure` 가 원본 body 로 판정.
- [ ] **필수 섹션 "채워짐" 검사(소유 무관·구조만)**(ADR D7·R15 agy): `behaviors:` 선언 정의의 필수 섹션은 **① 실제 본문** 또는 **② 유효한 섹션 포인터**가 있으면 통과. 섹션 이름을 하드코딩하지 않는다. **포인터 문법은 `> BEHAVIOR: <name>` 한 줄 고정**(정규식 `^ {0,3}>\s*BEHAVIOR:\s*([a-z0-9]([a-z0-9-]*[a-z0-9])?)\s*$` — 들여쓰기 3칸까지·**이름은 디렉토리명 규칙**(`\S+` 는 `../x` 경로 탈출을 허용해 폐기·R18 agy HIGH))이고 **코드펜스 안은 제외**한다(R17 양 엔진: 정규식만 쓰면 예제 문자열을 포인터로 오인하고 들여쓴 포인터를 놓친다). `<name>` 이 그 파일의 `behaviors:` 에 있고 실재해야 유효 — 본문을 heuristic 하게 읽지 않는다(R16). **빈 heading 만 있으면 잡힌다.** *채점기는 의미를 판정할 수 없으므로 소유를 묻지 않는다 — D1(내용 유형 소유)과 충돌하던 것을 이렇게 해소했다*
- [ ] ⚠ **섹션별 파싱 로직 신설**(R11 양 엔진 HIGH — 선결): 현행 `completenessMissing` 은 heading 만 남기고 `scoreStructure` 는 전체 줄 수만 센다. **특정 heading 에 속한 본문을 분리해 보는 로직이 없다.** 인자 추가로는 불가 — 본문을 heading 단위로 분할해 **섹션별 실체 줄**을 세는 파서를 먼저 만든다 `scoreStructure` 시그니처를 "구조 검사용 body"와 "줄 수 계산용 body"로 **나눠 받도록 확장**할 것(함수 분리는 불필요·인자 추가로 충분). 공유 BEHAVIOR 는 참조하는 정의마다 줄 수가 반복 계산되며 **이는 의도된 동작 — 테스트로 고정**할 것. 구현 시 BEHAVIOR 본문도 **사전 읽기**로 가져온다.

- [ ] 현행 필수 섹션(`SKILL.md:113` — 핵심 역할·작업 원칙·입출력 프로토콜·에러 핸들링·협업)과의 **매핑표** 작성 → `agent-design-patterns.md`
- [ ] **강제하지 않고 권장**으로 추가(기존 5개 섹션과 충돌하지 않음: 에러 핸들링 ⊂ Recovery, 작업 원칙 ⊃ Intent/Decision)

- **순서:** §단계 순서·의존의 그래프가 단일 권위다(여기서 반복하지 않는다 — 세 곳에 흩어져 서로 어긋났던 원인). 요약하면 **트랙 3개는 서로 독립**이고, **트랙 2·3 은 그래프에 명시된 선행 의존만 순차**다(화살표 `→` 와 B3·B4 의 인프라 선행 게이트 `└─` 를 모두 포함 — "화살표만"이라 쓰면 그 게이트가 배제된다). **트랙 1 내부 4건은 서로도 독립**이라 순서가 없다.
- **모든 단계:** 외부리뷰(codex+agy·러너 제외) **2R 이상 · HIGH 0 · MEDIUM 0 2연속** · 측정 꼬리 발행 · 결과서 + `check-artifacts.sh` · 단일 커밋.
- **전파 범위는 단계마다 다르다 — 일괄로 "전 생성 하네스 전파"라 쓰지 말 것**(R8 codex MED. 근거는 `harness-update.sh:48` 의 `MANAGED_RELS` 7항목과 생성 번들 실측):

  | 단계 | 실제 전파 범위 | 근거 | 전파 기인 최소 게이트 |
  |---|---|---|---|
  | 정본 정정 | **전파 없음** — 팩토리 내부 문서만 | `loop-self-eval.md` 는 `MANAGED_RELS` 미등록·생성 번들 미포함(§218). 생성본이 되는 `external-review-loop.md` 엔 해당 오서술 0건 | 정책감사·외부리뷰(회귀 드라이런 불요) |
  | B1 | **둘로 쪼개진다** — ⓐ `check-behaviors.sh`(검증기)**만** 기존 하네스까지(`MANAGED_RELS` 등록 시) · ⓑ **BEHAVIOR 파일·`CLAUDE.md`/`AGENTS.md` 포인터는 신규 생성분만** | updater 는 `MANAGED_RELS` 의 **파일 복사만** 한다(`harness-update.sh:48`) — Phase 5 산출물(`:247`)을 기존 하네스에 소급 생성하지 않는다 | ⓐ **중대** · ⓑ 정책감사·외부리뷰 |
  | B2 | **신규 생성분만** | `agent-design-patterns.md` 는 생성 시점 입력(`SKILL.md:75·80·90`)이나 `MANAGED_RELS` 미등록 → 기존 하네스는 재생성 전까지 안 받음 | 정책감사·외부리뷰 |

  **등급 합성 규칙(중요):** 이 표의 마지막 열은 **전파에서만 도출한 최소 게이트**다. 최종 리스크 등급은
  **`max(전파 기인, 안전 기인)`** 이다 — 전파가 0이어도 안전상 중대일 수 있다. **B4 가 그 예다**: 전파는
  없지만 삭제 판정 가드라 등급은 **중대**를 유지한다(제안서 §3 B4). 반대로 **B1 은 전파 기인으로 중대가
  되므로 절의 `등급:` 줄도 중대로 맞춘다.** 표와 절의 `등급:` 줄이 어긋나면 **높은 쪽이 권위**다.

  **⚠ 표에 없는 단계 — P0-M:** 위 표는 기존 요약줄이 지목하던 4단계만 대체한다. P0-M 은 **설계와 구현을
  나눠서** 봐야 한다.

  - **P0-M 설계 = 전파 없음 · 등급 중대(안전 기인).** 산출물이 설계서다. 중대인 이유는 전파가 아니라
    **측정 강제라는 구조적 안전 리스크**이며(제안서 §3-0), 이는 B4 와 같은 계열이다 — 위 합성 규칙의
    "전파 0이어도 안전상 중대" 사례. **전파로 등급을 재귀속시키지 말 것.**
  - **P0-M 구현 = 전파 범위 미확정(설계 수렴 후 판정).** 확정된 사실은 하나다: P0-M 이 언급하는
    `build-scorecard.sh`·`emit-loop-scorecard.sh`·`run-review.sh` 가 **셋 다 `MANAGED_RELS` 에 있다**
    (7항목 중 3개). 그러나 **구현이 이 파일들을 반드시 고친다는 보장은 없다** — 수용 기준이 요구하는 것은
    "호출자 **외부**의 fail-closed 장치"(§P0-M 수용 기준)이지 특정 파일 수정이 아니고, 현 구조에서
    `run-review.sh` 는 리뷰 실행기일 뿐 scorecard 발행은 Step 8 의 별도 호출이다
    (`external-review-loop.md:214·216`). 새 외부 게이트·wrapper·hook 으로 강제하면 세 파일을 안 고칠 수도 있다.
    → **조건부로 기록한다:** *설계가 등록 스크립트를 고치는 쪽을 택하면 기존 하네스로 전파되며 그때 중대다.*
    실제 수정 파일·전파 규모·구현 등급은 **설계 수렴 후 전용 구현 절에서 확정**한다.

  **"P0-M 구현" 전용 절이 없다** — 순서 줄에만 등장한다. **착수 전 전용 절을 먼저 작성하라.**
  절 없는 단계에 게이트만 걸어두면 공수표다(무엇을 게이트할지가 안 적혀 있다).

  **판정 규칙:** 어떤 단계를 "중대 blast-radius"로 올리려면 **그 단계가 건드리는 파일이 `MANAGED_RELS` 에 있거나 생성 번들에 포함된다는 것을 먼저 실측**하라. "정본 디렉토리에 있으니 전파된다"는 추측이다 — `skills/myharness/references/` 안에도 전파되지 않는 내부 문서가 있다.
