# ADR-001 — 행동 요구의 아티팩트 소유권

상태: **채택**(B0) · 날짜: 2026-08-30 · 선행: 없음 · 후속: B1(BEHAVIOR.md 포맷 채택)
근거: 제안서 §3 B0 · 참고자료 `../agentbehavior-reference.md` · **현행 코드 실측**(아래)

## 맥락

BEHAVIOR.md 를 도입하면 같은 행동 요구가 **에이전트 정의·스킬 절차·BEHAVIOR·holdout
assertion** 네 곳에 중복될 수 있다. "top-level 점수축을 늘리지 않는다"만으로는 이 다층
drift 를 막지 못한다(제안서 §3 B0). B1 착수 전에 소유권을 확정한다.

### 실측한 현재 상태 (추측 아님)

| 사실 | 확인 방법 |
|---|---|
| 에이전트 정의 필수 섹션 5종 = 핵심 역할·작업 원칙·입출력 프로토콜·에러 핸들링·협업 | `skills/myharness/SKILL.md:113` |
| frontmatter 연결 계약 = 에이전트 `skills:` · 오케스트레이터 스킬 `orchestrates:` | 같은 줄 |
| 계층A 4축은 **파일 파싱만** 한다(트리거·구조·유도·가지치기) | `artifacteval.ts` `scoreTrigger`·`scoreStructure`·`scoreInduction`·`scorePruning` |
| **holdout 은 `harness-ui/src` 에 0건** | `grep -rn holdout harness-ui/src` |
| **`run-benchmark.sh` 미구현 — 실행 불가** | `factory-map.md:28` |

이 두 부재가 ADR 의 범위를 정한다: **없는 인프라를 전제한 규약은 쓰지 않는다**(계획서 R-1).

## 결정

### D1. 단일 정본 — 행동 요구는 BEHAVIOR 가 소유한다

행동 요구 1건의 정본은 **`BEHAVIOR.md`** 다. 에이전트 정의·스킬 절차는 그것을 **구현**한다.

우선순위: `BEHAVIOR.md` > 에이전트 정의 > 스킬 절차.
충돌 시 BEHAVIOR 가 이긴다. 단 **BEHAVIOR 가 없는 요구는 정의·절차가 정본**이다 —
BEHAVIOR 를 안 쓰는 하네스가 정상이며(B1 은 권장이지 필수가 아니다) 그 경우 현행이 그대로다.

**중복 금지 규칙:** 같은 요구를 BEHAVIOR 와 정의 양쪽에 **문장으로 적지 않는다.**
정의는 BEHAVIOR 를 **참조**하거나, BEHAVIOR 가 없을 때만 직접 기술한다.

**참조 형식(R1 codex MED — 형식이 없으면 dead/orphan 을 결정적으로 판별할 수 없다):**

- **위치:** 정의 파일 **frontmatter** 의 `behaviors:` 배열. 본문 링크가 아니다 —
  본문은 자유 서술이라 파싱이 heuristic 이 되고, frontmatter 는 이미 `skills:`·`orchestrates:`
  연결 계약이 쓰는 자리다(`SKILL.md:113`). **같은 관례를 따른다.**
- **값:** BEHAVIOR 디렉토리명(`.agents/behaviors/<name>/BEHAVIOR.md` 의 `<name>`).
  경로가 아니라 이름 — 경로를 쓰면 디렉토리 구조가 바뀔 때 전부 깨진다.
- **대상:** 에이전트 정의(`.claude/agents/*.md`)와 스킬(`SKILL.md`) 둘 다 쓸 수 있다.
- **미선언의 의미:** `behaviors:` 가 **없으면** "이 정의는 BEHAVIOR 를 쓰지 않는다"이지
  "미마이그레이션"이 아니다. `skills:` 의 `link_unknown` 과 **다르게 취급한다** —
  BEHAVIOR 는 권장이지 필수가 아니므로 미선언이 부채가 아니다.

**부분 도입의 경계 — 파일 단위 전면 이관(R1 codex · R2 양 엔진 정정):**

`behaviors:` 를 선언한 정의 파일은 **그 파일의 행동 요구 전부**를 참조 BEHAVIOR 집합이
소유한다. 선언하지 않은 정의는 전부 정의가 정본이다. **중간은 없다.**

> ⚠ 처음엔 "그 BEHAVIOR 가 **다루는 범위**에서 정본"이라고 썼는데 **자기모순이었다**(R2 양 엔진).
> "다루는 범위"를 판단하려면 결국 사람이 문장 단위로 읽어야 하고, 그게 바로 피하려던
> "요구 단위 소유"다. 게다가 범위를 기계적으로 식별할 필드가 없어 **어떤 문장이 중복인지
> 판별할 수 없다.** 파일 단위라고 했으면 파일 단위여야 한다.

**"행동 요구"의 경계 — 내용 유형으로 긋는다(R4 양 엔진 · 세 번째 정정):**

| 내용 유형 | 소유 | 판별 질문 |
|---|---|---|
| **판단 기준** — 왜·언제 하나, 무엇을 결론짓나, 실패·모호할 때 어떻게 하나, 무엇을 하면 안 되나 | **BEHAVIOR** | "이걸 바꾸면 **행동이 달라지나**?" |
| **구조·인터페이스·배선** — 정체성, 입출력 형식·필드, 통신 대상, 연결 계약(`skills:`·`orchestrates:`) | **정의** | "이걸 바꾸면 **형식·대상만** 달라지나?" |

**두 질문이 모두 "예"일 때 — 행동이 이긴다(R5 codex MED):**
실제 문장은 둘을 겸한다. 예: `stabilizer.md:31` 의
`"1회 재시도 후 재실패 시 해당 게이트 결과 없이 진행(누락 명시), 상충 데이터 삭제 금지·출처 병기"`
는 **진행·삭제 금지**(행동)와 **누락 명시·출처 병기**(형식)를 동시에 규정한다.

**우선순위: 행동 > 형식.** 한 문장이 행동을 규정하면 그 문장은 BEHAVIOR 소유다.
형식 부분은 **정의에 별도 문장으로 다시 쓴다**(같은 문장을 양쪽에 두는 게 아니라 **쪼갠다**).
위 예라면:
- BEHAVIOR(`Recovery`): "1회 재시도 후 재실패면 그 게이트 결과 없이 진행한다. 상충 데이터를 삭제하지 않는다."
- 정의(입출력 프로토콜): "게이트 결과 누락 시 누락 사실을 명시한다. 상충 데이터는 출처를 병기해 보고한다."

**분해 단위는 문장이다.** 한 문장이 두 유형을 겸하면 **두 문장으로 나눈다.**

**분해가 불가능하다고 판단되면** 그건 대개 문장이 너무 뭉뚱그려진 것이다.
그래도 못 나누겠으면 **정의에는 행동 문장을 남기지 않는다** — 참조와 인터페이스 조각만 남기고
행동은 BEHAVIOR 로 보낸다. (R5 codex: "못 쪼개면 정의에 남긴다"는 앞서의 처리는 **중복 금지와
정면 충돌**했다 — 행동 문장이 정의에 남으면 단일 정본이 깨진다.)

**커스텀 섹션**(필수 5종 밖·예: `## 게이트 3층`)도 **같은 판별 질문**을 적용한다.

> ⚠ **경계를 세 번 고쳤다.** R2 "파일 단위 전면 이관" → R3 "섹션명 단위" → R4 "내용 유형".
> 섹션명으로 기계적으로 나누는 방식이 실제 파일에서 깨진 근거(R4 양 엔진이 실측):
> - `stabilizer.md` 의 **에러 핸들링**은 실패 시 행동과 **보고 형식**이 한 문장에 섞여 있다(`:28-31`).
> - `stabilizer.md` 의 **팀 통신 프로토콜**에 `"게이트 조율·판정만. …월권 금지"` 라는 **행동 경계**가 있다(`:36`).
> - `harness-ui-planner.md` 의 **협업**에도 `"코드 구현은 하지 않는다"` 가 있다.
>
> 즉 섹션명은 내용 유형을 보장하지 않는다. **판별 단위는 문단이되, 기준은 위 두 질문**이다.
> (R3 에서 "문장 단위로 쪼개지 않는다"고 했던 것은 *기준 없이* 쪼개지 말라는 뜻이었다 —
> 기준이 있으면 쪼갤 수 있고, 없으면 판별이 자의적이 된다. 기준을 준다.)

**따라서:** BEHAVIOR 가 판단 기준을 **전부** 가져갔을 때 `behaviors:` 를 선언한다.
(6차원↔5섹션 **상세 매핑표는 B2** 가 만든다. 여기서는 소유 기준만 정한다.)

### D7. 채점 중립성 — 규약을 따를수록 점수가 떨어지면 안 된다

**문제(R4 agy HIGH):** `scoreInduction`(`artifacteval.ts:142-148`)은 **명령형 줄 비율**과
원인 키워드로 점수를 낸다. 판단 기준(명령형이 가장 밀집한 부분)을 BEHAVIOR 로 옮기면
남은 정의의 명령형 비율이 떨어져 **4축 점수가 깎인다.** 규약을 지킬수록 손해다.

**결정: 참조 대상 BEHAVIOR 본문을 함께 읽어 4축을 계산한다.** 정본이 옮겨갔으니 채점 대상도
따라간다. B2 착수 전에 구현한다.

> ⚠ **"induction 축만 제외" 안은 폐기했다(R5 agy HIGH — 채점 우회 통로다).**
> BEHAVIOR 본문을 안 읽으면 `induction` 만 빠지는 게 아니라:
> - `scoreStructure` 의 **줄 수 초과 감점**(`artifacteval.ts:134`)을 내용을 옮겨 **부당하게 우회**한다.
> - 옮겨간 내용 안의 **중복 문장이 `scorePruning`(`:152`) 대상에서 통째로 사라진다.**
>
> 즉 평가 잣대 자체가 무력해진다. 값싼 쪽을 고르면 규약이 **점수 회피 수단**이 된다.

**축별 입력 계약(R6 양 엔진 — "4축에 함께 넣는다"만으로는 구현 불가):**
`scoreTrigger` 는 frontmatter `description` 을, 나머지 축은 `body` 를 받는다
(`artifacteval.ts:103·116·142·152`). 그러니 축마다 입력이 다르다.

| 축 | 입력 | 왜 |
|---|---|---|
| `trigger` (`scoreTrigger`) | **정의의 description 만** | 트리거는 정의의 frontmatter 계약이다. BEHAVIOR 는 트리거를 규정하지 않는다 |
| `induction` (`scoreInduction`) · `pruning` (`scorePruning`) | **합성 body** | 내용이 옮겨간 축들이다. 합성하지 않으면 명령형 비율이 떨어지고(R4) 중복 검출이 사라진다(R5) |
| `structure` (`scoreStructure`) | **검사마다 다르다 — 아래 표** | 한 함수 안에 성격이 다른 검사 6종이 있다(R7 양 엔진) |

**`scoreStructure` 안의 검사별 입력(R7 양 엔진 — "필수 섹션 + 줄 수"로만 나눈 것이 부족했다):**

| 검사 | 입력 | 왜 |
|---|---|---|
| **필수 섹션 누락**(`completenessMissing`·`:163`) | **정의 body**(합성 전) — 통과 기준은 **본문 또는 섹션 포인터**(소유 무관·아래) | 필수 섹션은 **정의 파일의 구조 계약**이다. BEHAVIOR 의 heading 을 정의 섹션으로 오인하면 안 된다 |
| **본문 부실**(현행 `n < 5` → 과락) | **정의 body**(합성 전) — 단 `behaviors:` 선언 정의는 **판정 기준을 바꾼다**(아래) | "정의가 실체 있는가"를 본다. BEHAVIOR 가 빈 껍데기를 대신 채워주면 안 된다. **그러나 줄 수로 재면 규약 준수가 처벌된다**(R8 codex) |
| **줄 수 상한**(skill `>500`·`>800` · agent `>400`) | **합성 body** — 단 finding 의 `range` 는 **생략**한다(아래) | 내용을 옮겨 감점을 우회하는 것을 막는 축이다(R5). 여기서 합산하지 않으면 D7 의 목적이 사라진다 |
| **`references/` 분리**(`!hasRefs && n > 300`) | **정의 body 의 줄 수**(합성 전) | *처음엔 합성 줄 수로 정했는데 틀렸다(R8 양 엔진).* 짧고 정상적인 정의가 큰 BEHAVIOR 를 참조하면 **분리할 내용이 없는데도** "references/로 분리하라"는 지시가 붙는다. 시키는 대로 해도 BEHAVIOR 소유 내용은 못 옮기고 **빈 `references/` 로 감점만 우회**하게 된다. `hasRefs` 와 줄 수가 **같은 구조 사실을 측정해야** 한다 |
| **대용량 코드펜스**(`>60줄`) | **합성 body** — `range` 생략·`why` 에 출처 표기 | *처음엔 정의 body 로 정했는데 우회 통로였다(R9 agy).* 60줄 넘는 코드펜스를 BEHAVIOR 에 넣으면 검사를 **통째로 빠져나간다.** BEHAVIOR 본문은 런타임 프롬프트에 그대로 합쳐지므로 컨텍스트 비대화는 똑같이 일어난다. 엉뚱한 파일 지목 문제는 **줄 수 상한과 같은 방식**(range 생략 + why 에 "참조 BEHAVIOR `<name>` 안" 표기)으로 푼다 |

즉 **분량·중복 계열(줄 수 상한·코드펜스)은 합성**하고, **정의 파일의 구조 계약**(필수 섹션·본문 부실·references 분리)은 정의 원본을 본다.
판별 원칙: *"내용을 옮겨 빠져나갈 수 있는 검사"는 합성하고, "정의 파일 자체의 형태를 보는 검사"는 원본을 본다.*
`scoreStructure` 는 현재 `body` 하나만 받으므로 **B2 에서 "구조 검사용 body"와 "줄 수 상한
계산용 body"를 나눠 받도록 시그니처를 확장**한다(함수를 쪼갤 필요는 없다 — 인자 추가로 충분).
`completenessMissing` 은 이미 별도 함수이고 호출 순서상 합성 전 body 를 넘길 수 있다(agy 확인).

**필수 섹션의 "채워짐" 기준 — 채점은 소유를 판정하지 않는다(R15 agy HIGH · 최종):**

> ⚠ **D1 과 충돌하던 것을 여기서 해소한다.** D1 은 소유를 **내용 유형(문단 단위)** 으로
> 가르는데, 앞서 D7 의 표는 **섹션 전체**를 "BEHAVIOR 소유 / 정의 소유"로 하드코딩했다.
> 한 섹션 안에 두 유형이 섞인다는 것이 D1 의 전제이므로 **"BEHAVIOR 소유 섹션"이라는
> 범주 자체가 성립하지 않는다.** 서로 다른 잣대였다.
>
> **근본 이유:** 채점기는 **의미를 판정할 수 없다**(D3 의 공백과 같다). 어떤 문단이 행동인지
> 형식인지 기계가 알 수 없으므로, **채점은 소유를 묻지 않고 구조만 본다.**

**섹션 포인터 문법 — 결정적으로 파싱 가능한 한 가지 형태만(R16 양 엔진 HIGH):**

```
> BEHAVIOR: <name>
```

**판독 규칙(R17 양 엔진 — 정규식만으로는 오탐·미탐이 난다):**

1. **코드펜스 안은 제외한다.** ` ``` ` 블록 안의 같은 문자열은 포인터가 아니다.
   (예제·설명으로 적은 문법이 포인터로 오인되면 빈 섹션이 통과한다 — 오탐.)
2. **줄 앞 공백은 3칸까지 허용**한다: `^ {0,3}>\s*BEHAVIOR:\s*(\S+)\s*$`.
   markdown 에서 3칸 이하 들여쓴 `>` 는 유효한 blockquote 다(4칸부터는 코드 블록).
   이걸 빼면 정상적으로 들여쓴 포인터를 놓친다 — 미탐.
3. 그 외에는 **한 줄에 정확히 매치**되는 형태만 인정한다(문장 중간·다른 텍스트와 같은 줄 불가).

**유효 조건:** `<name>` 이 ① 그 파일의 frontmatter `behaviors:` 배열에 선언돼 있고
② 실재하는 BEHAVIOR 여야 한다. 둘 중 하나라도 아니면 포인터가 아니다(= 그 섹션은 부실).

**frontmatter 와 본문 포인터가 어긋날 때:** frontmatter 가 단일 출처이므로
`behaviors:` 에 없는 이름을 본문이 가리키면 **포인터로 인정하지 않는다**(위 유효 조건 ①).
반대로 `behaviors:` 에 있는데 본문 포인터가 없는 것은 정상이다 — 그 섹션에 실제 본문이
있으면 되고, 없으면 부실로 잡힌다.

> ⚠ **D1 과의 모순을 여기서 해소한다.** D1 은 "본문은 자유 서술이라 파싱이 heuristic 이 된다"며
> 참조를 frontmatter 로 한정했는데, D7 이 "본문 참조 포인터"를 기계로 식별하라고 요구해
> **정면 충돌**이었다(R16 양 엔진).
> → **frontmatter 가 여전히 참조의 단일 출처**다(D1 불변). 본문 포인터는 **자유 서술이 아니라
> 고정 문법 한 줄**이고, 그 값이 frontmatter 에 있는지 대조해서만 유효해진다.
> 즉 본문을 heuristic 하게 읽는 게 아니라 **정해진 형태를 정확히 매치**한다.

**채점 규칙(소유 무관·구조만):** `behaviors:` 를 선언한 정의에서 필수 섹션은
**① 실제 본문이 있거나 ② 위 문법의 유효한 섹션 포인터가 있으면** 통과한다. 둘 다 없으면 부실이다.
- 섹션 이름을 하드코딩하지 않는다 — 어느 섹션이든 같은 규칙이다.
- 내용을 BEHAVIOR 로 옮긴 섹션은 ②로 통과하고, 안 옮긴 섹션은 ①로 통과한다.
- **빈 heading 만 있는 섹션은 어느 쪽도 아니므로 잡힌다** — agy 가 R10 에서 지적한 우회가
  여기서 막힌다(그때는 소유별로 나눠 막으려 했는데, 소유를 몰라도 막을 수 있다).

**소유(D1)는 사람이 지키는 작성 규약이고 리뷰가 확인한다.** 채점기는 소유를 강제하지 않는다.
그 한계를 여기 적어 둔다 — "채점을 통과했으니 소유 규약도 지켜졌다"고 읽으면 안 된다.

**추가 계약 2가지(R8 양 엔진):**

**(1) 줄 수 상한 finding 은 `range` 를 붙이지 않는다.**
현행은 `range: "1-${n}"` 을 단다(`artifacteval.ts:125`). `n` 이 합성 줄 수면 **정의 파일에
존재하지 않는 줄**을 수정 범위로 가리킨다(target anchor 는 정의 파일이다).
→ `range` 를 **생략**하고, `why` 에 `정의 N줄 + 참조 BEHAVIOR M줄 = 합계 K줄` 형태로
내역을 적는다. 사람이 어디를 줄여야 하는지는 그 내역으로 판단한다.

**(2) `behaviors:` 선언 정의의 "본문 부실" 판정은 줄 수가 아니라 구조로 한다.**
D1 대로 판단 기준을 BEHAVIOR 로 보내면 정의 body 가 얇아진다. 필수 heading 이 2개뿐인
스킬은 heading + 참조 포인터만으로 유효한데, 현행 `n < 5` 규칙은 그걸 **무조건 D 과락**시킨다.
**규약을 지킬수록 손해**라 D7 채점 중립성과 정면 충돌한다(R8 codex).
→ `behaviors:` 를 선언한 정의는 아래 **4가지를 모두** 만족할 때 실체 있는 것으로 본다.
줄 수 하한(`n < 5`)은 적용하지 않는다.

1. **필수 heading 이 모두 있다.**
2. **선언한 참조가 전부 실재한다**(끊긴 참조 0).
3. **참조된 BEHAVIOR 가 비어 있지 않다** — 6차원 중 최소한 `Intent` 와 `Failure modes` 에
   heading 외 본문이 있다(B1 `check-behaviors.sh` 계약에 추가).
4. **정의에 실체가 남아 있다** — 필수 섹션 중 **최소 하나**에 참조 포인터가 아닌 실제 본문이 있다.
   *소유를 묻지 않는다(위 규칙과 같은 이유 — 채점기는 의미를 판정할 수 없다).*
   전부 참조 포인터뿐이면 그 정의는 껍데기다.
   *검사 주체: `scoreStructure`(정의 원본 body 로 판정·R10 양 엔진 — 처음엔 조건만 적고
   누가 검사하는지 안 정해 어느 단계도 구현 책임을 갖지 않았다).*

**"실체 줄"의 정의(R10 codex MED — 안 정하면 결정적으로 검사할 수 없다):**
아래를 **모두 제외**하고 남은 줄이 1줄 이상이면 실체가 있다.
- 공백만 있는 줄 · markdown heading(`#`~`######`)
- **섹션 포인터 줄** — 위 문법(`> BEHAVIOR: <name>`)에 매치되는 줄
- 주석(`<!-- … -->`) · 수평선(`---`)
- 코드펜스 **경계**(` ``` `) — 펜스 **안의 내용은 실체로 센다**

> ⚠ *처음엔 ①②만 두고 "빈 껍데기 + 가짜 참조는 `check-behaviors.sh` 가 막는다"고 썼는데,
> **그 주장이 실제 검사 범위보다 강했다**(R9 양 엔진). 그 스크립트는 위치·frontmatter·참조
> 실재만 본다. 그래서 **heading 만 있는 빈 정의**가 **내용 없는 BEHAVIOR** 나 **다른 정의용
> BEHAVIOR** 를 가리켜도 통과했다.* ③④를 더해 막는다.
>
> **남는 한계(자동 검증 불가):** 참조한 BEHAVIOR 가 **그 정의와 실제로 관련 있는가**는
> 의미 판단이라 검출하지 못한다(D3 의 공백과 같은 계열). 무관한 BEHAVIOR 를 가리켜
> 형식 요건만 채우는 것은 **사람 리뷰에서 잡아야 한다** — B1 게이트의 외부리뷰가 그 자리다.
> 이 공백을 "검출된다"고 오해하지 않도록 여기 적어 둔다.

**합성 방식:** 정의 body 뒤에 참조 BEHAVIOR body 를 **그대로 이어 붙인다**(append).
BEHAVIOR 의 heading 을 정의 구조로 오인하지 않도록 **필수 섹션 검사는 합성 전 body 로**
한다(위 표). 이것이 축별로 입력을 나눈 이유다.

**공유 BEHAVIOR 주의(R6 codex):** 여러 정의가 같은 BEHAVIOR 를 참조하면 그 줄 수가
**참조하는 정의마다 반복 계산**된다. 이는 의도된 동작이다 — 각 정의는 자기가 의존하는
분량만큼 무게를 진다. 다만 **B2 구현 시 이 성질을 테스트로 고정**해 나중에 "버그"로 오인해
바뀌지 않게 한다.

**구현 시 유의(agy):** `evaluateArtifacts` 의 정의 순회는 본문을 미리 읽어둔 뒤 동기적으로
채점한다. BEHAVIOR 본문도 **같은 방식으로 사전 읽기**가 필요하다(순회 안에서 비동기 읽기를
하면 결정성·동시성 제한이 깨진다).

> **한계 — 점수와 런타임의 간극(R6 agy·판단 갈림):** 채점기는 정의와 BEHAVIOR 를 **합친 것**을
> 보지만 실행 시 에이전트는 **두 문서를 오가며** 읽는다. 그 간접 비용은 점수에 반영되지 않는다.
> agy 는 이를 "평가가 런타임을 대변하지 못한다"고 봤고, codex 는 "D2 는 생성 규칙·D7 은 평가
> 읽기라 충돌이 아니다"라고 봤다. **간극이 있다는 사실만 기록한다** — 지금 측정할 수단이 없고,
> 측정 없이 한쪽으로 정하면 또 다른 추측이 된다. 계층B·holdout 이 생기면 실측으로 판단한다.

### D2. 파생물 생성 규칙 — 파생하지 않는다(현 단계)

**BEHAVIOR 에서 무엇도 자동 생성하지 않는다.** 정의·절차는 **손으로 쓰고 BEHAVIOR 를 참조**한다.

근거: 자동 파생은 생성기·재생성 시점·승인 경로가 필요한데 그중 무엇도 실재하지 않는다.
파생을 도입하면 "정본이 바뀌었는데 파생물이 안 따라감"이라는 새 drift 축이 생긴다 —
막으려던 문제를 늘리는 셈이다. **파생은 B3 이후 재검토**한다.

### D3. drift 검출 — 계층A 에 얹지 않는다. 별도 검사다

`check-behaviors.sh`(B1 신설)가 **구조적 정합만** 본다:
- BEHAVIOR 위치·frontmatter 필수 필드(`name`·`description`)·디렉토리명 일치
- 정의가 참조하는 BEHAVIOR 가 **실재하는가**(끊긴 참조 = dead_link 계열)
- BEHAVIOR 가 **어떤 정의에서도 참조되지 않는가**(고아)

**의미 수준의 일치(정본과 구현이 같은 말을 하는가)는 검출하지 않는다.** 그건 계층B(LLM)
영역이고 현재 없다. 없는 능력을 규약으로 약속하지 않는다.

**계층A 4축에 얹지 않는 이유:** 4축은 `md-agent`·`md-skill`·`toml-agent` rubric 으로
**정의 파일 자체**를 채점한다. BEHAVIOR 는 다른 종류의 파일이라 같은 축으로 재면 점수 의미가
섞인다(제안서 AE8 "종류별 rubric"). 별도 검사가 맞다.

> ⚠ **범위 한정(R6 codex):** 여기서 금지하는 것은 **BEHAVIOR 를 독립 아티팩트로 채점해
> 롤업에 별도 행으로 올리는 것**이다. D7 이 규정하는 "참조 BEHAVIOR 본문을 정의 채점의
> **입력에 합성**"하는 것과는 다르다 — 후자는 정본이 옮겨간 만큼 채점 대상도 따라가는 것이지
> 새 아티팩트를 만드는 게 아니다.

### D4. lifecycle — 삭제·rename 은 참조 무결성만 책임진다

| 사건 | 처리 |
|---|---|
| BEHAVIOR **삭제** | 참조하던 정의가 **dead 참조**로 잡힌다(`check-behaviors.sh`). 정의를 고치거나 BEHAVIOR 를 복원할 때까지 **fail**. 자동 삭제·자동 수정 없음 |
| BEHAVIOR **rename** | 삭제 + 신설로 본다. 참조 갱신은 **사람이** 한다(자동 rename 추적 없음 — 없는 기능을 약속하지 않는다) |
| 생성 하네스 전파 | `check-behaviors.sh` 는 `MANAGED_RELS` 등록 대상이라 `update`(7-7)로 전파된다. **BEHAVIOR 파일 자체는 전파되지 않는다**(Phase 5 산출물이라 신규 생성분만) — 계획서 §게이트·순서 요약의 B1 행과 같다 |
| holdout | **해당 없음.** holdout 인프라가 실재하지 않는다(위 실측). B3 에서 도입될 때 이 ADR 을 개정한다 |

### D5. 실행 테스트 동기화 — 트리거 규약은 지금 발효, 벤치마크·holdout 은 B3 이월

제안서 §3 B0 의 대상은 두 종류인데 **실재 여부가 다르다**(R1 양 엔진 — 처음엔 둘 다 없다고
잘못 판정했다):

| 대상 | 실재 | 처리 |
|---|---|---|
| **트리거 검증 쿼리**(should / should-NOT, 각 8~10개) | **실재한다** — `SKILL.md:371` Phase 6-4, 완료 체크리스트에도 있다(`:482`) | **지금 규약을 세운다**(아래) |
| 벤치마크·holdout | 없다 — `run-benchmark.sh` 미구현(`factory-map.md:28`)·`harness-ui/src` 에 holdout 0건 | **B3 로 이월** |

**트리거 검증 동기화 규약(지금 발효):**

1. BEHAVIOR 의 **`Intent`(왜·언제) 또는 `Failure modes`** 가 바뀌면, 그 BEHAVIOR 를
   `behaviors:` 로 참조하는 정의의 **should / should-NOT 쿼리를 재검토 대상으로 표시**한다.
   - 왜 이 두 차원인가: `Intent` 는 "언제 트리거되나"를, `Failure modes` 는 "무엇이
     트리거되면 안 되나"를 정한다. should/should-NOT 쿼리와 **직접 대응**한다.
   - 나머지 4차원(`Evidence`·`Decision`·`Execution`·`Recovery`)은 트리거가 아니라 **실행**을
     규정하므로 쿼리 재검토를 요구하지 않는다.
2. **어디서 누가 하는가(R2 양 엔진 — "표시한다"만으로는 실행 불가능한 규약이다):**
   - **호출 지점:** `SKILL.md` **Phase 6-4(트리거 검증)** 와 **완료 체크리스트(`:482`)**.
     BEHAVIOR 를 고친 변경은 이 단계를 **반드시 거친다**. 별도 도구를 만들지 않는다 —
     이미 있는 관문에 건다.
   - **판별 수단:** 사람이 **BEHAVIOR 파일의 diff 를 읽고** `Intent`·`Failure modes` 절이
     바뀌었는지 본다. 자동 검출기는 없다(만들지 않는다 — D3 과 같은 이유).
   - **기록 대상:** 그 작업의 **결과서**(`docs/**/working_history/*.md`).
   - **필수 필드 4개:** ① 바뀐 BEHAVIOR 이름 ② 바뀐 차원(`Intent` / `Failure modes` / 둘 다)
     ③ 영향받은 정의(`behaviors:` 로 그것을 참조하는 파일) ④ 쿼리를 **재생성했는지 그대로
     두었는지와 그 이유**.
   - **미기록 시:** 게이트가 자동으로 막지는 않는다(아래 경고 참조). 리뷰에서 지적 대상이다.
3. **대상은 스킬이다 — 에이전트는 `N/A` 로 기록한다**(R3 양 엔진):
   Phase 6-4 는 **"각 스킬의 description"** 트리거를 검증한다(`SKILL.md:371`). 에이전트에는
   대응하는 트리거 쿼리가 **없다**. 따라서 BEHAVIOR 를 **에이전트 정의만** 참조하는 경우
   필수 필드 ④(재생성 여부)를 채울 대상이 없다.
   → 그 경우 **④에 `N/A(에이전트 참조 — 트리거 쿼리 대상 없음)` 를 적는다.** 빈칸으로 두지
   않는다(빈칸은 "안 했다"와 구분되지 않는다).
   **에이전트용 트리거 검증을 새로 만들지 않는다** — 없는 절차를 규약이 요구하면 지킬 수 없다.
   필요해지면 `SKILL.md` Phase 6-4 개정으로 다루고 이 ADR 을 개정한다.
4. **영향받은 정의를 찾는 수단:** `behaviors:` 역인덱스 도구는 **없다.**
   `rg "behaviors:" -A3 .claude/agents .claude/skills` 로 사람이 찾는다.
   B1 의 `check-behaviors.sh` 가 고아 검출을 하므로 **그 출력이 역인덱스 역할을 겸할 수 있다** —
   B1 에서 참조 목록을 함께 출력하도록 한다(ADR 이 요구하는 최소 기능).
3. **자동 무효화는 하지 않는다.** 자연어 명세 변경이 쿼리를 무효로 만드는지는 의미 판단이고
   그 능력이 없다(D3 과 같은 이유). 없는 능력을 규약으로 약속하지 않는다.

> ⚠ **자동 강제 장치가 없다는 것을 분명히 한다.** 처음엔 `check-artifacts.sh` 가 BEHAVIOR
> 변경 기록을 강제한다고 적었는데 **사실이 아니었다**(R1 codex) — 그 스크립트는 결과서
> 최소 크기와 `## 다음 단계 참조` heading 만 검사한다(`:19-22`).
> 위 규약은 **Phase 6-4 관문에 걸린 사람의 절차**이지 기계 검사가 아니다.
> Phase 6-4 를 건너뛴 변경은 이 규약을 조용히 우회할 수 있다(R2 codex).
> **그 한계를 감수한다** — 자동 검출은 의미 판단이라 능력이 없고, 없는 능력을 약속하는 것보다
> 한계를 적어두는 편이 낫다. 검출 자동화는 계층B 도입 시 재검토한다.

### D6. UI 노출 계약 — 5번째 축을 만들지 않는다

`#/eval` 최상위 노출은 **4축 카드 1개**를 유지한다(P0-c 에서 이미 지킨 불변).
BEHAVIOR 관련 정보는:

- **보인다:** `check-behaviors.sh` 결과를 **구성 건강도 진단(접기)** 안에 — 기존 findings
  분류(고아·dead_link)와 같은 자리. P0-c 가 만든 진단 뷰를 재사용한다.
- **안 보인다:** 별도 점수·별도 카드·5번째 축. `rollup.axisAvg` 에 축을 추가하지 않는다.

**코드 계약(B1 에서 테스트로 고정):** `Axis` 유니온은 `trigger|structure|induction|pruning`
4개를 유지한다. 축을 늘리려면 이 ADR 을 먼저 개정해야 한다.
(`artifacteval.ts` 의 `export type Axis` 가 리터럴 유니온이라 테스트로 고정 가능하다 — 실측 확인.)

**B1 의 UI 통합 범위(R1 codex MED — 안 정하면 구현자가 CLI-only 인지 UI 연결인지 모른다):**

- **B1 은 CLI 까지다.** `check-behaviors.sh` 가 사람·CI 가 읽는 출력을 내는 것으로 끝낸다.
- **UI 연결은 하지 않는다**(B1 범위 밖). 연결하려면 서버 어댑터·응답 스키마·finding 분류·
  집계 주체를 정해야 하는데, 그건 `harness_scorecard` 의 `FindingType` 유니온을 늘리는
  일이라 **P0-c 가 확정한 진단 뷰 계약을 건드린다.**
- ⚠ **따라서 "진단 접기 안에 보인다"는 위 결정은 B1 완료 시점에 아직 참이 아니다**(R2 양 엔진).
  채택된 결정의 관찰 가능한 결과가 어느 단계에서도 구현되지 않으면 ADR 이 거짓말을 한다.
  → **`B5 — BEHAVIOR 진단 UI 연결` 단계를 신설**해 계획서에 등록한다(B1 후속).
  그 단계가 끝나기 전까지 D6 의 UI 부분은 **미래 목표**이지 현재 사실이 아니다.
- **finding 표현은 여기서 확정한다(R3 codex — ADR 이 "유력"이라 하고 계획서가 "확정"이라
  하면 구현자가 어느 쪽을 따를지 모른다):** 새 `FindingType` 을 만들지 않고 **기존
  `dead_link`·`orphan` 에 `subject_kind: "behavior"` 로 얹는다.**
  근거: 분류를 늘리면 `FindingType` 을 소비하는 집계·UI·테스트가 전부 갈라진다. `subject_kind`
  는 이미 `agent|skill|pointer|runtime` 유니온이라 값 추가가 같은 계열의 확장이다.
  **B5 선검증에서 이 가정이 깨지면**(예: 기존 UI 가 `subject_kind` 를 분기해 렌더 못 함)
  그때 이 ADR 을 개정한다 — 선검증 결과가 결정을 뒤집을 수 있음을 명시한다.
