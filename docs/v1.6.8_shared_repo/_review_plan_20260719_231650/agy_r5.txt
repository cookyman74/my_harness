### 2. 이전 지적(R1~R4) 닫힘 여부 및 질문 답변

**Q. R1/R2/R3 지적이 실제로 닫혔는가? 물리 게이트가 진짜 강제인가?**
*   **완벽히 닫혔습니다.** 로컬 `pre-commit`은 우회 가능한 편의성 도구로 명시하고, 실제 강제를 GitHub Actions의 **Branch Protection (Required Status Checks)**로 이관한 점(`§0-3`)은 완벽한 물리 게이트입니다.
*   스캐너의 S1 전진 배치, 캐시 샌드박스/파싱 방어(YAML `safe-load`, 깊이 상한, `core.symlinks=false`)의 S0 적용, 그리고 마이그레이션 시 raw hash가 아닌 **canonical 정규화 후 파싱 트리 비교**(`§4-1`)를 채택함으로써 R1~R3의 갭과 모순이 완전히 해소되었습니다.

**Q. (i) R4: verdicts 위조의 "신뢰 경계 명시"가 정직한 종착으로 타당한가? 무한회귀를 끊었나?**
*   **매우 타당한 정직한 종착점입니다.** 로컬에서 생성된 텍스트 산출물(verdicts)에 대해 암호학적 증명을 요구하는 것은 하드웨어 엔클레이브가 없는 환경에서 불가능합니다. 이를 억지로 CI에서 증명하려 들지 않고, **"부주의 및 외부 위협 방어 + 우회 가시성 확보"**로 목적을 명확히 한 뒤, 위조를 위해서는 `CODEOWNERS`를 무력화할 **내부자 2인 결탁**이 필요하도록 비용을 높인 것은 git 기반 dev-tool이 취할 수 있는 가장 올바른 위협 모델입니다. 무한 회귀를 정확히 끊어냈습니다.

**Q. (ii) R4: CI pwn-request 방어(default 브랜치 워크플로)가 실효인가?**
*   **실효성이 확고합니다.** untrusted PR이 실행될 때 `pull_request_target`을 금지하여 악의적인 코드가 권한을 탈취하는 경로를 막았고, `GITHUB_TOKEN`을 read-only로 제한하며 평가 워크플로에 시크릿을 주입하지 않음(`§0-3`)으로써, PR 단계에서의 exfiltration(정보 유출)이나 토큰 탈취를 원천 봉쇄했습니다. PR 작성자가 워크플로 자체를 변조해 통과를 위장하려 해도 머지 단계에서 `CODEOWNERS` 승인에 막히므로 안전합니다.
