작업계획서(`plan.md`)에 대한 외부감사(R4) 결과를 보고합니다. R1~R3의 지적사항(스캐너 S1 전진 배치, 마이그레이션 정규화 비교, 네임스페이스 폴백 금지, safe-parse 등)이 설계서와 계획서에 충실히 반영되어 있습니다.

특히 마이그레이션 무결성을 `canonical 정규화 의미동등 비교`로 보강한 점과, `P-2 매핑 불성립 시 S2 차단 및 정규화 폐기`로 의존성을 명확히 격리한 점은 설계적으로 매우 훌륭합니다.

하지만 CI 게이트의 **물리적 강제력**과 관련된 실행 환경에서 중대한(HIGH) 모순과 헛점이 발견되었습니다. 아래는 스코프 내 남은 HIGH/MED 지적 사항입니다.

### 📌 감사 지적 사항

1. **HIGH** | `2. S0 — 레지스트리 규약 + 평가` & `0-3. 게이트 자기 무결성` | **CI 워크플로 실행 컨텍스트 오염 (Supply Chain RCE 및 우회)**
   - **근거:** 팀 공유 레지스트리는 같은 저장소 내의 브랜치 PR을 사용합니다. GitHub Actions의 기본 `pull_request` 이벤트는 **PR 브랜치 내에 포함된 워크플로 파일**을 실행합니다. 계획서에 CODEOWNERS로 게이트 로직 변조를 막는다고 명시되어 있으나, 이는 "최종 병합(Merge)"만 막을 뿐 **악성 워크플로의 즉시 실행**을 막지 못합니다.
   - **실패 시나리오:** 공격자(또는 감염된 팀원)가 PR을 올릴 때 `.github/workflows/eval.yml`을 수정하여 평가 단계를 `exit 0`으로 치환하거나, CI 환경의 `GITHUB_TOKEN`을 외부로 유출(exfil)하는 코드를 삽입합니다. CI가 푸시 즉시 이를 실행하므로 필수 상태 체크는 "GREEN"으로 조작되고, 시스템 시크릿이 유출될 수 있습니다.
   - **해결 방안:** PR 평가 CI는 반드시 `pull_request_target` 트리거를 사용하여 타겟 브랜치(main)의 신뢰할 수 있는 워크플로 로직만 실행하도록 강제하거나, CI 권한 격리에 대한 체크리스트를 S0에 추가해야 합니다.

2. **HIGH** | `0-3. 커밋·병합 게이트` | **"수기 위조 차단"의 논리적 모순 (위조 불가 실패)**
   - **근거:** 계획서에는 CI가 `verdicts.json`을 통해 summary를 재생성하고 원시 리뷰 파일(`*_r*.txt`)의 존재 여부를 검사해 위조를 막는다고 명시되어 있습니다. 그러나 이 파일들은 모두 로컬에서 사용자가 자체적으로 생성하여 커밋하는 파일입니다. 로컬에서 생성된 파일을 기반으로 CI가 위조 여부를 판단하는 것은 논리적으로 불가능합니다.
   - **실패 시나리오:** 엄격한 `no-high 2연속` 룰을 우회하고 싶은 사용자가, 실제 리뷰를 수행하지 않고 가짜 `no-high` 상태의 `verdicts.json`과 더미 원시 텍스트 파일을 만들어 커밋합니다. CI는 재생성된 summary가 조작된 `verdicts.json`과 일치한다고 판단하여 게이트를 그대로 통과시킵니다. 물리적 게이트가 우회됩니다.
   - **해결 방안:** 로컬 파일 기반으로는 완벽한 위조 방지가 불가능함을 인정하고 "위조 불가" 주장을 문서에서 철회해야 합니다. 대신 이를 "팀 내 상호 리뷰 시 해당 산출물 검토"라는 **팀 신뢰(Team Trust)** 영역으로 편입시키거나, 완벽한 물리적 통제를 원한다면 CI 서버 측에서 LLM 검토를 직접 수행하도록 게이트 구조를 변경해야 합니다.

3. **MED** | `3-1. RegistryClient` | **스코프 중복 설정 시 충돌 해결책 누락**
   - **근거:** 네임스페이스 기반으로 소스를 고정해 의존성 혼동을 막은 설계(R3 반영)는 매우 적절합니다. 하지만 사용자가 로컬 `registries` 설정에 **동일한 스코프(예: `@corp/*`)를 여러 레지스트리에 중복 등록**할 경우의 충돌 해결 정책이 없습니다.
   - **실패 시나리오:** 두 레지스트리가 같은 스코프를 가질 때, 첫 번째 레지스트리가 실패하면 두 번째로 폴백되어 제한적인 의존성 혼동 공격이 재발하거나, 어떤 레지스트리가 선택될지 알 수 없는 비결정적인(non-deterministic) 다운로드 문제가 발생합니다.
   - **해결 방안:** 앱 실행 전 설정 로드 시점에 중복 스코프 등록을 발견하면 하드 에러(fail-closed)로 동작을 차단하는 로직을 S1 체크리스트에 추가해야 합니다.

4. **MED** | `0-4b. 공통 mutation·읽기 보안 게이트` | **확장성을 고려하지 않은 엄격한 JSON 크기 상한 (Self-DoS)**
   - **근거:** untrusted 캐시 리더가 모든 파일에 대해 파일 크기 상한과 일괄적인 `JSON.parse` 크기 상한을 적용합니다. 레지스트리가 활성화되면 전체 카탈로그인 `index.json`은 자연스럽게 커집니다.
   - **실패 시나리오:** 스킬과 에이전트가 누적되어 `index.json` 파일 크기가 일괄 상한(예: 1MB)을 넘어서는 순간, 모든 정당한 팀원 클라이언트가 카탈로그를 읽지 못해 레지스트리 전체가 멈추는 서비스 거부(DoS)가 발생합니다.
   - **해결 방안:** `index.json`과 같은 메타데이터 집계 파일은 크기 상한을 별도로 넉넉하게 예외 처리하거나, 스트리밍 JSON 파서(JSONStream 등)를 사용하도록 계획서에 명시하여 보안과 확장성 충돌을 방지해야 합니다.

5. **LOW** | `0-4b. 공통 mutation·읽기 보안 게이트` | **git clone 시 심링크 생성 허용 방치**
   - **근거:** 앱 레벨에서 `lstat`으로 읽기를 거부하므로 안전하긴 하지만, `git clone` 옵션에 `-c core.symlinks=false`가 누락되어 있어 악성 심링크 파일이 로컬 워크트리에 물리적으로 생성되는 것 자체는 허용하고 있습니다.
   - **실패 시나리오/해결 방안:** 악성 심링크가 생성되는 원천 경로를 막기 위해 심층 방어 차원에서 `clone` 인자에 해당 옵션을 추가하는 것이 좋습니다.
