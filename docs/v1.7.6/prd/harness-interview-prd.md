## 1. 배경 — 왜 지금인가

지금 myharness 는 **사용자가 던진 요청 한 덩어리만 가지고** 하네스를 만든다.
도메인 문장을 읽고, 에이전트를 나누고, 게이트 강도를 정하고, 검증 항목을 쓴다 — **전부 추론으로**.

하네스는 이후 모든 작업의 기반이다. 프로젝트 팀 구성과 같아서, 여기서 어긋나면
그 뒤의 모든 실행이 어긋난 채로 진행되고 **한참 뒤에야 드러난다**.

### 1-1. 실측 — 팩토리는 지금 아무것도 묻지 않는다

| 확인 | 결과 |
|---|---|
| `SKILL.md` 에 사용자 **질문** 단계 | **없음**. `질문` 이 나오는 두 곳은 "질문 수준으로 숙련도를 파악"(56행)과 "단순 질문은 직접 응답"(278행) |
| Phase 0-4 사용자 **확인** 단계 | **있음** — *"감사 결과를 사용자에게 요약 보고하고, 실행 계획을 확인받는다"*(50행). 그러나 확인받는 것은 **팩토리의 실행 계획**이고, **작업의 제약**(완료 기준·비가역·승인)은 묻지 않는다 |
| Phase 1-5 사용자 숙련도 | **묻지 않고 감지한다** — *"대화의 맥락 단서(사용 용어, 질문 수준)로 기술 수준을 파악"* |
| Phase 0 현황 감사 | 산문 지시뿐 — `Glob`·`Read`·`ls`·`find` 실행 지시가 **0건**(§HI9) |

**팩토리의 현재 스탠스는 "묻지 않고 추론하고, 계획만 확인받는다"** 이다.
사용자 접점(Phase 0-4)은 이미 있다 — 인터뷰는 **그 접점에 들어간다.** 새 접점을 만드는 것이 아니다.

### 1-2. 추론으로 때우고 있는 것 두 가지 — 실측

**(가) 리스크 등급을 추측한다.** `SKILL.md:319-321` 의 등급표는 이미 **비가역성**을 기준으로 쓰고 있다.

| 등급 | 기준(정본 원문) |
|---|---|
| 경량 | 1파일 · **가역** · 테스트 無 (오타·문구·설정) |
| 표준 | 다파일 · 기능 추가 |
| 중대 | 계약 변경 · **비가역** · 다도메인 |

**그런데 "이 작업에서 무엇이 비가역인가"를 아는 사람은 사용자뿐인데, 팩토리는 물어보지 않는다.**
배포·마이그레이션·외부 발송·과금 — 요청 문장에 안 적혀 있으면 팩토리는 모른다.
등급을 낮게 추측하면 게이트가 통째로 약해지고, 높게 추측하면 원칙 7이 경고한 "과의식"이 된다.

**더 근본적으로 — 등급을 판정하는 단계 자체가 없다.** `SKILL.md` 에서 `등급` 은 원칙 7(15행)·5-6 표(315·317행)·
체크리스트(487행)에만 나온다. **"이 하네스는 어느 등급인가"를 결정하는 Phase 가 없다.** 표는 있는데
그 표를 적용하는 절차가 없으니, 등급은 오케스트레이터가 암묵적으로 정한다. 실 소비처는 있다 —
`external-review-loop.md:38-39` 가 `축소종결판정(등급)` 으로 등급을 **입력**으로 받는다. 입력을 만드는 곳이 비어 있다.

**(나) Phase 6 검증에 도메인 완료 기준이 없다.** Phase 6 전체(6-1 구조 · 6-2 실행 모드 · 6-3 스킬 실행 ·
6-4 트리거 · 6-5 드라이런 · 6-6 테스트 시나리오, 332~394행)에서 `완료`·`수용`·`기준`·`성공` 이 나오는 줄은
**0건**이다(grep 실측). 6-1 항목이 대표적이다:

```
· 모든 에이전트 파일이 올바른 위치에 있는지 확인
· frontmatter 검증(skills:·orchestrates: 배열)
· 에이전트 간 참조 일관성 확인
· 커맨드가 생성되지 않았는지 확인
```

전부 **"하네스가 잘 만들어졌는가"** 다. 6-6 도 *"정상 흐름 1개 + 에러 흐름 1개 기술"* — 오케스트레이터 시나리오다.
**"이 작업이 성공했는가"** 를 보는 항목이 하나도 없다.
사용자에게 완료 기준을 묻지 않았으니 쓸 수가 없다.

### 1-3. 안 물은 질문의 답은 사라지지 않는다 — 뒤에서 청구된다

이 레포에 증거가 있다.

| 사건 | 어느 갈래인가(§3) | 실제 발견 시점 |
|---|---|---|
| **측정 꼬리 누락** — 오케스트레이터가 `verdicts.json → build-scorecard` 를 이어받지 않아 **자기평가가 한 번도 실행되지 않음** | ① 사용자만 아는 것 — "이 하네스의 성과를 무엇으로 측정합니까?" 를 묻지 않았다 | M14/M15 외부감사 **~22라운드 뒤**, 사용자 지적으로(CLAUDE.md 2026-07-10) |
| **"재사용" 오표기**(F8 crypto·owner/mode 가 코드에 미실재) | ② 기계가 실측할 것 — 설계서가 "재사용"이라 썼지만 **코드에 없었다**. 스캔(HI9)이 잡는 종류 | 하네스 3 구축 시 설계서 코드근거 검증 12/13 에서(CLAUDE.md 2026-07-09) |

첫 줄이 핵심이다. **앞에서 5분 물을 것을 뒤에서 22라운드에 지불했다.**
둘째 줄은 인터뷰가 아니라 **스캔**의 근거다 — 사람에게 "무엇이 있습니까"를 물으면 같은 오표기가 답으로 돌아온다.

> 하네스 3 정의 파일 소실(2026-07-26 확인)은 여기 넣지 않는다. 원인은 `.claude/` 가 추적 대상이 아니었던 것(이슈 #7,
> `.gitignore` allowlist 로 해결)이고, **인터뷰 질문으로 예방되는 종류가 아니다.** 근거 없는 사례를 늘리지 않는다.

## 3. 무엇을 물을 것인가 — 세 갈래로 갈린다

전부 묻는 설계는 자동화의 목적을 되돌린다. 쟁점마다 **누가 답을 아는가**가 다르다.

| 갈래 | 예시 | 처리 |
|---|---|---|
| **① 사용자만 아는 것** | 무엇이 되면 끝인가 · 무엇이 비가역인가 · 누가 승인하는가 | **묻는다** |
| **② 기계가 실측해야 하는 것** | 어떤 에이전트·스킬이 이미 있나 · 어떤 CLI 가 깔려 있나 | **묻지 말고 스캔**(HI9) |
| **③ 물어도 사용자가 모르는 것** | 에이전트 몇 명 · 어떤 모델 · 게이트 몇 단계 | **묻지 말고 설계**(팩토리 본업) |

**②를 물으면 사용자의 기억을 실측 대신 쓰게 된다.** v1.7.5 에서 `gpt-5.4-mini` 가 HTTP 400 을 낸 것,
gemini CLI 가 `IneligibleTierError` 를 낸 것이 "안다고 생각한 게 틀린" 사례다.

**③을 물으면 부담이 사용자에게 되돌아간다.** 프로바이더 가이드의 처방은 서로 반대다
(Fable 5 "프롬프트를 걷어내라" vs Astra "성향별 보정을 더해라") — 이걸 사용자가 판정할 수 없다.

### 3-1. ①과 ②는 화면에서는 하나로 합친다

가용 집합 = **스캔 ∩ 정책** 이라 어느 한쪽만으로는 답이 안 나온다.
그래서 질문은 추상 정책이 아니라 **실측된 구체 선택지** 위에서 던진다.

```
이미 있는 것: doc-syncer · release-manager · repo-qa · stabilizer (프로젝트 4)
             smoke-agent (전역 · 배치 대상 아님)
→ 이 작업에서 되돌릴 수 없는 것이 있습니까?
```

**다만 저장할 때는 끝까지 가른다.** 재검증 가능성이 다르기 때문이다(§HI7).

## 4. 기능 요구 — HI1~HI13

### HI1. 질문의 형태 — **전 문항 객관식 · 기본값과 추천을 병기**
사용자에게 답을 **생성**하게 하지 않는다. 요청과 스캔에서 읽어낸 것을 **선택지로 제시하고 고르게 한다.**
자유 서술 문항은 두지 않는다.

```
② 이 작업에서 되돌릴 수 없는 것은?  (복수 선택 · 번호 입력 · 엔터=기본값)
   1. GitHub Release 발행        ← 기본 · 추천
   2. npm publish                ← 추천
   3. main 브랜치 force push
   4. 없음 — 전부 되돌릴 수 있다
   5. 그 외(직접 입력)
   근거: 요청에 "릴리스"·CHANGELOG 갱신이 포함됨 → 1·2 추천 /
         기본은 **안전한 쪽**(비가역 있음 = 중대 등급)
```

**객관식이어야 하는 이유는 편의만이 아니다.** 산문 답은 파싱해야 하고, 파싱은 모호하고,
모호하면 **HI5 결선과 HI6 차분 회귀가 성립하지 않는다.** 답이 열거값이면 "답 → 소비처"가 표가 되고,
"답 A·B 로 생성해 diff" 가 결정적으로 실행된다. **객관식은 검증 가능성의 전제다.**

#### HI1-1. 기본값과 추천은 **다를 수 있다** — 뭉치면 fail-closed 가 깨진다

| 표기 | 의미 | 선정 원칙 |
|---|---|---|
| **기본** | 무응답·엔터 시 진행할 값(HI4) | **안전한 쪽.** 틀렸을 때 손해가 작은 쪽 |
| **추천** | 이 요청 맥락에서 최적으로 판단한 값 | 요청·스캔 근거 기반 |

둘이 갈리는 예: 요청이 오타 수정이면 **추천**은 "비가역 없음(경량)"이지만,
**기본**은 "비가역 있음(중대)" 이어야 한다. 무응답이 위험한 쪽으로 흐르면 안 된다 —
`external-review-loop` 이 리뷰어 축소 시 중대 등급에서 `BLOCKED` 를 돌려주는 것과 같은 원칙이다.

**같을 때는 한 줄로 합쳐 표기한다**(`← 기본 · 추천`). 다를 때만 두 줄로 갈린다.

#### HI1-2. 표기 형식을 고정한다
표기가 세션마다 흔들리면 답 파싱이 깨진다.

- 답은 **번호로 받는다.** 텍스트 매칭은 오타·표기 차이에 깨진다
- 각 선택지에 `← 기본` / `← 추천` 마커. 없으면 없다
- 문항마다 **근거 한 줄** 필수 — 왜 그것을 추천하는지. Astra 가이드의 "지시 우선순위 명시"와 같은 취지
- 문항 머리에 **답변 방식**(단일/복수 · 엔터=기본)을 명시

#### HI1-3. 초안 반박은 유지된다 — 객관식은 그 형태를 바꾼 것이다
"요청에서 이렇게 읽었습니다 → 틀린 것 있습니까"의 정신은 **선택지에 기본·추천을 미리 찍어두는 것**으로
구현된다. 사람은 생성보다 교정이 쉽고, 객관식은 교정을 **한 글자**로 줄인다.

**이것은 신규 발명이 아니라 이 레포가 이미 확립한 패턴이다** — harness-eval M-y 의
"AI 초안 → 검토 큐 → 일괄 적용", F10 의 "폼 AI 초안 → 승인 → 저장".

**수용 기준:** ① 자유 서술 문항이 **0개**다 ② 모든 선택지에 기본·추천 마커가 계산되어 붙는다
③ 기본값은 항목별로 "안전한 쪽"이 무엇인지 문서에 정의되어 있다 ④ 모든 문항에 근거 한 줄이 있다.

### HI2. 묻는 것 — 다섯 항목
하네스 **구조를 실제로 바꾸는 것**만 묻는다.

| # | 항목 | 유형 | 기본값(=안전한 쪽) | 없으면 무엇이 망가지는가 |
|---|---|---|---|---|
| 1 | **완료 판정 기준** — 무엇이 되면 끝인가 | 복수 | 기계 검증 가능한 항목 전부 | 검증 에이전트가 **무엇을 검사할지 모른다.** 이 레포의 지배적 실패 계열("0건 검사하고 통과")의 근원 |
| 2 | **비가역성 경계** — 되돌릴 수 없는 것 | 복수 | **비가역 있음**(→ 중대) | 리스크 등급을 추측하게 된다(§1-2 가) |
| 3 | **실패 비용의 비대칭** — 오류 vs 지연 | **단일** | 오류가 더 아프다 | 외부리뷰 라운드·TDD 적용 여부의 근거가 없다 |
| 4 | **승인 지점** — 사람이 반드시 봐야 하는 곳 | 복수 | 비가역 직전 전부 | 승인 사다리를 팩토리가 지어낸다 |
| 5 | **기존 자산** — 이미 있는 팀·규칙·도구 | 복수 | 스캔이 찾은 것 전부 | 중복 에이전트가 누적된다(`SKILL.md:98`·`138` 이 이미 경고) ← HI9 스캔이 초안을 만든다 |

**유형이 갈리는 이유:** ②④⑤는 **여러 개가 동시에 참**이다. 단일선택으로 만들면 답을 잃는다.
③만 배타적이다(오류와 지연 중 무엇을 먼저 포기하는가). **단일선택 일률 적용은 정보 손실이다.**

#### HI2-1. Phase 0 분기별 적용 — 네 분기가 다르다
`SKILL.md:37-40` 은 현황에 따라 **신규 구축 / 기존 확장 / 운영·유지보수 / 업데이트** 로 갈린다. 인터뷰는 분기마다 다르게 붙는다.

| Phase 0 분기 | 인터뷰 | 근거 |
|---|---|---|
| **신규 구축** | ①~⑤ 전부 | 구조를 처음 정한다 |
| **기존 확장**(에이전트·스킬 추가·아키텍처 변경) | ②(비가역)·⑤(기존 자산)만 + 기존 전제(HI8) 표시 | Phase 선택 매트릭스가 "Phase 1 건너뜀(Phase 0 결과 활용)"이라 ①③④는 기존 답을 잇는다 |
| **운영·유지보수**(7-5) | 없음 — HI8 전제를 **보여주기만** | 구조를 바꾸지 않는다 |
| **업데이트**(7-7) | 없음 | 정본 재전파. 사용자 수정 보존이 목적 |

**수용 기준:** 분기마다 어느 문항이 뜨는지 테스트로 고정한다. 운영·업데이트 경로에서 문항이 뜨면 실패.

**모델 관련 항목(외부 반출 가부 · 비용 성향)은 v1.7.6 에서 묻지 않는다.**
소비처가 v1.7.7(MA2·MA7)에 생기기 때문이다 — **소비처 없는 수집 금지**(HI5). 소급 가능하므로 미뤄도 손실이 없다.

**수용 기준:** 다섯 항목 각각에 §6-2 결선표의 소비처가 **하나 이상** 존재한다. 소비처 없는 항목은 묻지 않는다.

### HI3. 질문 수는 스캔이 정한다 — 상한은 질문 수가 아니라 **생성 부담**
스캔이 선택지를 좁히면 질문은 소멸한다. 없는 선택지는 제시하지 않는다.

앞서 검토 과정에서 "질문 3개 상한"을 제안했다가 **철회했다.** 하네스 구성 전체로 보면 항목 수를 깎는 것이
목적이 아니다. 제약은 **"사용자가 처음부터 만들어내야 하는 답의 양"** 에 걸어야 하고, HI1(초안 반박)이 그 답이다.

**수용 기준:** 초안이 확정적으로 도출되는 항목은 **확인만 받고 질문하지 않는다.**

### HI4. 비대화 경로 — 인터뷰가 blocking 이면 안 된다
팩토리는 자동·CI 경로에서도 호출된다. 인터뷰가 응답을 기다리면 거기서 멈춘다.

**수용 기준:** ① 무응답이면 **기본값**(HI1-1 — 안전한 쪽, *추천값이 아니다*)으로 진행한다
② 환경변수로도 답을 줄 수 있다 — 객관식이므로 **번호로 받는다**
(`run-benchmark.sh` 의 `BENCH_ALLOW_EXEC` 선례) ③ **가정으로 진행했다는 사실이 산출물에 남는다** —
조용히 기본값을 쓰면 그것이 이 레포의 지배적 실패 계열이다.

### HI5. 답 → 산출물 **결선(結線)** — 이 릴리스에서 가장 중요한 요구
**물어놓고 아무도 읽지 않는 것**이 이 설계의 제일 큰 위험이다.

> **실측 전례:** `REVIEWERS_OVERRIDE` 를 런처가 export 했는데 `run-review.sh` 에 **그것을 읽는 코드가 없었다.**
> 라운드마다 네 프로세스가 같은 산출물에 동시에 썼고, 한 파일에 "새 결함 없음"과 "[HIGH] 2건"이 공존해
> **R11 을 통째로 무효 처리**했다. 아무도 오래 몰랐다.

인터뷰는 이 실패의 완벽한 서식지다 — 질문은 뜨고, 사용자는 답하고, 답은 변수에 담기고,
**정작 Phase 3 에서 아무도 안 읽는다.**

**수용 기준:** 모든 인터뷰 항목이 §6-2 결선표에 **소비처와 확인 방법**을 갖는다. 결선 없는 항목은 삭제한다.

### HI6. 차분(差分) 수용 기준 — "질문이 뜬다"는 수용 기준이 아니다
효과는 **답을 바꾸면 산출물이 달라지는가**로만 검증한다.

| 답을 바꾸면 | 달라져야 하는 것 |
|---|---|
| 완료 판정 기준 | Phase 6 검증 항목 |
| 비가역 경계 | Phase 5-6 리스크 등급 |
| 실패 비용 비대칭 | 외부리뷰 라운드 하한 · TDD 적용 |
| 승인 지점 | 오케스트레이터 승인 사다리 |

**전 문항 객관식(HI1)이 이 회귀를 성립시킨다.** 답이 열거값이라 A·B 를 기계가 지정할 수 있고,
같은 선택지가 결정적으로 재생성되므로(HI11) diff 가 답 변경 때문인지 생성 요동 때문인지 구분된다.
자유 서술이었다면 이 테스트를 쓸 수 없다.

**수용 기준:** 답 A·B 로 하네스를 각각 생성해 **diff 가 비어 있지 않음**을 회귀 테스트로 고정한다.
**기본값으로만 생성한 하네스와 추천값으로 생성한 하네스도 비교 대상**이다 — 둘이 같으면
기본·추천 분리(HI1-1)가 실효 없다는 뜻이다.

### HI7. 출처 구분 기록 — `scanned` 와 `declared` 는 섞으면 안 된다
화면에서는 하나로 합치되(§3-1), 프로파일에는 출처를 남긴다.

```
assets.agents      { value: [doc-syncer, ...], source: scanned,  at: 2026-09-10 }
policy.irreversible{ value: [release, publish], source: declared, at: 2026-09-10 }
```

**재검증 가능성이 다르다.** `scanned` 는 다시 돌리면 자동 갱신된다.
`declared` 는 **기계가 재검증할 방법이 없다** — 조직의 정책이 바뀌었는지 스캔으로 알 수 없다.

섞어두면 부패 감사가 `declared` 항목까지 "검증했다"고 통과시킨다. 그것이 곧
**"검사가 도는 것처럼 보이는데 그 항목은 안 봤다"** 이다.

**수용 기준:** 정책 감사가 `declared` 항목을 자동 통과시키지 않고 **"사람 확인 필요"로 분리 보고**한다.

### HI8. 전제 명시 — 하네스가 무슨 위에 서 있는지 보여야 한다
초기 답이 틀렸을 때의 경로가 필요하다. 구조가 그 전제 위에 섰는데 전제가 깨지면 조용히 어긋난다.

**정본은 프로파일이고 `CLAUDE.md` 는 포인터다.** 5-4 는 *"CLAUDE.md에 넣지 않는 것: 에이전트 목록, 스킬 목록,
디렉토리 구조, 실행 규칙 상세"* 를 규정하고 그 이유를 단일 출처로 든다(`SKILL.md:288`). 전제도 같은 원칙을 따른다 —
다섯 항목의 답·출처(HI7)·날짜는 **프로파일 파일**에 두고, `CLAUDE.md` 에는 **가정으로 넘어간 항목**과 프로파일 경로만 적는다.
가정 항목을 `CLAUDE.md` 에 두는 이유는 그것이 사람이 다음 세션에서 **가장 먼저 봐야 할 것**이기 때문이다.

**듀얼 출력이다.** 원칙 8·5-4 가 `AGENTS.md` 동시 출력을 요구하고, 정책 감사 #7 이 **듀얼런타임 parity** 를 검사한다.
`CLAUDE.md` 에만 쓰면 감사에 걸린다.

**수용 기준:** ① 프로파일에 다섯 항목 + 출처 + 날짜가 있다 ② 생성된 `CLAUDE.md`·`AGENTS.md` 양쪽에
**"전제"** 절(가정 항목 + 프로파일 경로)이 있고 정책 감사 #7 을 통과한다 ③ Phase 7(하네스 진화)·생성 하네스의
Phase 0(컨텍스트 확인, `orchestrator-template.md:45`)이 이 절을 재확인 트리거로 쓴다.

### HI9. 에이전트 스캔 — 산문 지시를 실행 가능한 계약으로 *(구 MA14 — v1.7.7 에서 이관)*
HI2 ⑤(기존 자산)의 초안은 스캔이 만든다. 그런데 지금 `SKILL.md:35` 는
*"`.claude/agents/`·`skills/`·`CLAUDE.md`를 읽는다"* 라는 **산문 지시**이고,
`Glob`·`Read`·`ls`·`find` 같은 실행 지시가 **한 건도 없다**. 전용 스크립트도 없다.

**실측 — 스캔 범위가 런타임과 다르다(이 머신):**

| 위치 | 개수 | Phase 0 이 읽는가 |
|---|---|---|
| `.claude/agents/` (프로젝트) | 6 | 읽음 |
| `~/.claude/agents/` (전역) | 1 | **안 읽음** |
| `~/.claude/plugins/**/agents/` | **35** | **안 읽음** |
| Claude 빌트인(`general-purpose`·`Explore`·`Plan` …) | 6 | **파일이 없어 읽을 수 없음** — 조회 명령도 없다 |
| `.codex/agents/*.toml` · `.agents/skills/` (듀얼 런타임) | 0 · 0 (이 레포) | `SKILL.md:35` 가 **읽으라고 이미 지시** — 스캔 계약이 덮어야 한다 |
| Codex 내장(`default`·`worker`·`explorer`) | 3 | `runtime-adapters.md:22` 기록. 파일 없음·버전 종속 |

(수치는 2026-09-10 이 머신 실측. 플러그인 35 는 앞선 검토에서 "5+"로 **과소 집계**했던 것을 정정한 값이다.)

**구현 언어: bash 가 아니라 Node(`.mjs`).**

| 후보 | 가용성 | 판단 |
|---|---|---|
| bash + `find`/`stat` | Windows 는 Git Bash 필요 · macOS bash 3.2 | **채택 안 함** |
| python3 | 있을 수도 없을 수도 | PR #6 이 *"python3 부재 시 검사 증발"* 을 지적한 전례 |
| **Node `.mjs`** | **Claude Code 자체가 Node 기반 — 사실상 보장** | **채택** |

> **정정:** bash 가 Windows 에서 "작동하지 않는" 것은 아니다 — `factory-ci.yml` 이 `windows-latest` 에서
> 정책 감사·회귀를 이미 돌리고 있고 v1.7.5 PR 도 통과했다. 문제는 **이식성 비용을 계속 지불한다**는 것이다:
> `stat -c` vs `stat -f` 플랫폼 차이가 **v1.7.5 R20 에서 HIGH 로 잡혔고**(GNU 는 `-f` 를 파일시스템 정보로
> rc 0 반환 → 폴백이 Linux 에서 영영 안 걸림), codex argv 다중행이 Windows/Git Bash 에서 첫 줄만 도달(PR #6),
> cp949/cp932 인코딩 오탐(PR #6). 파일시스템 탐색 + frontmatter 파싱은 이 비용이 가장 크게 드는 작업이다.
> **선례도 있다** — `harness-scorecard.md:39` 가 같은 이유로 `node scripts/harness-scorecard.mjs` 를
> *"portable 실행"* 이라 부르며 채택했고, "팩토리가 하네스 생성 시 타겟 `scripts/` 에 복사"까지 배선돼 있다.

**출력 계약**(`check-review-tools.sh` 의 `REVIEWERS:`·`SHADOWED:` 선례 — "없음"과 "있는데 못 씀"을 구분):

```
RUNTIME:        claude 2.1.267           ← `claude --version` 실측 형식 "2.1.267 (Claude Code)" 에서 추출
AGENTS_PROJECT: doc-syncer release-manager repo-qa ...
AGENTS_GLOBAL:  smoke-agent
AGENTS_PLUGIN:  conversation-analyzer code-simplifier ...   (35)
AGENTS_CODEX:   none                     ← .codex/agents/*.toml · ⚠ codex exec 는 이름 호출 불가(이슈 #8, runtime-adapters:40)
AGENTS_BUILTIN: claude=unknown codex=default,worker,explorer(문서 기준·버전 종속)
MODEL:          doc-syncer=opus release-manager=opus ...    ← 관측값. 티어(deep/standard/light)는 v1.7.7 MA1 이후
UNKNOWN_FIELDS: harness-ui-planner:{newField}   ← 정의 포맷 변경 감지
```

**`UNTIERED:` 는 이 릴리스에 없다.** 티어 개념은 v1.7.7(MA1)이 도입한다. v1.7.6 은 `MODEL:` 에 **관측된 값**만 적고,
v1.7.7 이 `MODEL:` 을 읽어 `UNTIERED:` 로 확장한다. 없는 개념을 미리 출력하면 그 줄은 항상 전원이 찍혀 무의미하다.

**범위 결정:** 전역·플러그인 에이전트는 **읽되 배치하지 않는다.** 중복 검토에는 필요하지만
남의 플러그인 에이전트에 티어를 붙이는 것은 월권이다.

**Claude 빌트인은 `unknown` 으로 보고한다.** `claude --help` 에 `--agent`·`--agents` 플래그만 있고
**목록 조회 명령이 없다**(실측). 하드코딩하면 `TeamCreate`/`TeamDelete` 제거(CLI v2.1.178) 때와 같은 부패가 재발한다.
Codex 내장 3종은 `runtime-adapters.md:22` 에 문서로 있으므로 **"문서 기준·버전 종속"** 을 붙여 출력한다 — 실측이 아님을 표기한다.

**버전 종속을 정면으로 다룬다:** 런타임 버전을 기록하고, 모르는 frontmatter 필드는 **버리지 않고 보고**한다.
조용히 무시하면 포맷이 바뀐 것을 아무도 모른다.

**스캔 오류가 사용자 승인으로 세탁되지 않게 한다.** 질문에 선택지를 제시할 때도 "없음"과 "PATH 밖"을 구분한다 —
nvm 다른 node 버전에 설치된 codex 가 **조용히 리뷰어에서 탈락한 채 "양 엔진 검증"으로 결과서에 기록된** 일이 있었다.

**수용 기준:** ① 같은 작업트리에서 두 번 실행하면 같은 출력(결정적) ② Linux·macOS·Windows CI 에서 **동일 출력**
③ 정의 포맷이 바뀌면 `UNKNOWN_FIELDS` 로 드러난다 ④ `SKILL.md:35` 가 읽으라고 지시한 **듀얼 런타임 경로 전부**를 덮는다
⑤ `MODEL:` 에 관측값이 있고 `model` 필드가 없는 정의는 `MODEL: x=none` 으로 드러난다.

### HI10. 실측 검증 — 인터뷰가 실제로 하네스를 좋게 만드는가
인터뷰는 배치보다 검증이 어렵다. 배치는 매핑표라 표로 확인되지만, 인터뷰는 **품질 판정**이 필요하다.
여기서 "물어봤으니 좋아졌겠지"로 넘어가면 v1.7.5 가 26종 잡아낸 거짓 통과가 재발한다.

**v1.7.5 산출물이 그대로 도구가 된다** — `run-benchmark.sh`(격리 실행·궤적 수집) +
`grade-trajectory.sh`(결정적 assertion) + 고정 케이스 9건. B3-lite 의 before/after 비교와 같은 방식이다.

**기존 케이스가 덮는 범위는 좁다.** `docs/v1.7.5/cases/gate-escalation/*.json` 9건은 `criteria` 가 **C1~C8 게이트 상승
행동** 전용이다(스키마 실측: `case_id`·`behavior`·`criteria`·`expectations`). 따라서 인터뷰 항목 중 **②비가역·③실패 비용
→ 등급 → 게이트 강도** 경로만 기존 케이스로 측정된다. ①완료 기준(→ Phase 6 항목)·④승인 지점·⑤기존 자산(→ 중복 판정)은
**신규 케이스가 필요**하다. 이것을 "기존 도구로 다 된다"고 쓰지 않는다.

**수용 기준:** ① 인터뷰 적용 전/후 하네스로 같은 고정 케이스를 돌린 **궤적 채점 결과**가 결과서에 있다
② ①④⑤ 항목은 신규 케이스로 측정하거나, 측정 불가를 **명시**한다 ③ 개선이 확인되지 않은 항목은 인터뷰에서 뺀다.

### HI11. 선택지 완전성 — 객관식이 **"선택지에 없는 답"을 잃지 않게** 한다
이것이 객관식의 유일한 구조적 약점이고, 이 레포에서 제일 위험한 형태의 약점이다.

비가역 후보를 4개 제시했는데 이 프로젝트의 진짜 비가역이 5번째라면, 객관식은 그것을
**조용히 없는 것으로 만든다.** 그리고 아무도 모른다 — **"검사가 도는 것처럼 보이는데
실제 대상을 안 봤다"** 는 이 레포의 지배적 실패 계열 그 자체다.

**해법 — 스캔의 `UNKNOWN_FIELDS` 와 같은 발상:** 모르는 것을 버리지 않고 **보고한다.**

| 규칙 | 내용 |
|---|---|
| 탈출구 필수 | 모든 문항에 **"그 외(직접 입력)"** 가 있다. 예외 없다 |
| 불완전 기록 | 탈출구가 선택되면 프로파일에 **`options_incomplete: true`** 와 입력값을 남긴다 |
| 진화 신호 | 같은 항목에서 탈출구가 반복 선택되면 **선택지 세트 개선 신호**로 Phase 7 이 집는다 |
| 선택지 생성 결정성 | 선택지는 **요청 + 스캔에서 도출**된다(고정 목록이 아니다). 같은 입력에 **같은 선택지**가 나와야 HI6 회귀가 성립한다 |

**수용 기준:** ① 탈출구 없는 문항이 생성되면 **생성 자체가 실패**한다(fail-loud)
② 탈출구 선택이 산출물에 기록된다 ③ 같은 요청·같은 작업트리에서 두 번 물으면 **같은 선택지**가 나온다.

### HI12. 런타임 렌더링 — 문항 스키마는 런타임 중립, 렌더러는 런타임별
Claude Code 에는 객관식 질문 도구(`AskUserQuestion`)가 있지만 **codex·agy 에는 없다.**
`runtime-adapters.md` 에 질문 기구 행이 **아직 없다**(실측) — 신설 대상이다.

**Claude Code `AskUserQuestion` 실측 제약**(이 릴리스의 설계를 직접 제약한다):

| 제약 | 값 | 설계에 미치는 영향 |
|---|---|---|
| 호출당 문항 수 | **1~4** | 다섯 항목 → **2회 호출**로 쪼갠다 |
| 문항당 선택지 수 | **2~4** | 비가역 후보가 5개면 **제시할 수 없다** → HI11 탈출구가 더 중요해진다 |
| 탈출구 | **"그 외"가 자동 제공** | 직접 추가하면 안 된다(중복). HI11 요구가 런타임에서 이미 충족 |
| 복수 선택 | `multiSelect` 지원 | HI2 의 복수 문항이 그대로 표현된다 |
| 헤더 길이 | 12자 | 항목 라벨을 짧게 유지 |

**따라서 문항은 런타임 중립 스키마로 정의하고, 렌더러를 갈아끼운다:**

```
문항 스키마(중립)  →  Claude Code(대화형): AskUserQuestion
                   →  codex·agy(대화형): 번호 목록을 텍스트로 출력 → 다음 사용자 턴에서 번호 수신  ← 폴백
                   →  codex exec · agy -p · claude -p(비대화): 렌더 없이 기본값(HI4) + 가정 표기
```

> **stdin 폴백은 쓰지 않는다.** PR #6 실측 — **agy 는 stdin 을 무시한다(argv 필수)**. 폴백은 "출력 후 다음 턴 수신"이어야
> 하고, 비대화 모드는 애초에 다음 턴이 없으므로 HI4 로 간다.
> **`claude -p` 에서 `AskUserQuestion` 이 어떻게 동작하는지는 미실측** — 설계서 착수 전 실측 항목이다.

**수용 기준:** ① 스키마에 런타임 고유 필드가 없다 ② 폴백 렌더러로도 같은 답을 받을 수 있다
③ `runtime-adapters.md` 에 질문 기구 행이 추가되고 런타임별 가용성이 기록된다
④ 선택지가 4개를 넘는 항목은 **묶거나 쪼개는 규칙**이 문서에 있다(제약을 조용히 넘기지 않는다).
